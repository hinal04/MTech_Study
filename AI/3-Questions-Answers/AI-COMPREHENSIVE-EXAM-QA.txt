Q1. AI vs ML vs DL Decision Framework for Real Estate [8 Marks]
[TYPE: Scenario-Based, Practical]

A real estate platform wants to automate three tasks:

**Task A**: Predict house price based on location, square footage, age, amenities
- Data: 100,000 historical house sales with final prices
- Need: Accurate price estimation for instant valuation

**Task B**: Identify fraudulent property listings (fake photos, misleading descriptions)
- Data: 500,000 property listings with images and descriptions
- Need: Flag suspicious listings before publication

**Task C**: Recommend properties to users based on browsing history
- Data: 2 million user-property interactions
- Need: Personalized recommendations in real-time

For each task, determine:

a) **Which category (Rules, ML, or DL) is most appropriate?** [2 marks]
b) **Justify with business and technical constraints** [3 marks]
c) **What would make you change your decision?** [2 marks]
d) **Estimate required data, timeline, and ROI** [1 mark]

**ANSWER:**

**a) Task A → Traditional ML; Task B → Deep Learning; Task C → Traditional ML [2 marks]**

**Task A - Traditional ML:**
- Structured data (numerical features: location, sqft, age, amenities)
- 100,000 samples: sufficient for gradient boosting (XGBoost, LightGBM)
- Clear features-to-target relationship (price ∝ location, size)
- Interpretability needed: Real estate agents need explanation ("price $50K lower due to age")
- DL unnecessary: Tabular data + small dataset = poor DL performance vs. ML

**Task B - Deep Learning:**
- Unstructured data: images and text descriptions
- 500,000 samples sufficient for CNN training
- Complex patterns: Fake photos have subtle artifacts, misleading text requires semantic understanding
- Rules insufficient: Fraudsters constantly evolve deception tactics
- Traditional ML struggles: Image feature extraction manual and limited

**Task C - Traditional ML (or Collaborative Filtering):**
- User-item interaction matrix well-suited for matrix factorization
- 2 million interactions: sufficient for ML recommenders
- Real-time serving: ML models faster than DL
- DL beneficial only if including rich content (product descriptions, images), which not mentioned

---

**b) Business & Technical Justification [3 marks]**

**Task A Constraints:**
- Budget: Real estate startup, moderate budget
- Timeline: 3-4 months feasible with ML
- Accuracy target: 85-90% acceptable (±$10K on $500K home)
- Interpretability: Critical (users won't trust black-box DL)
- **Decision**: XGBoost with feature importance analysis

**Task B Constraints:**
- Latency: Moderate (content review before publishing, can wait 5 seconds)
- Safety-critical: False positives (blocking legitimate listings) harmful; false negatives (allowing fraud) costly
- Data richness: 500K images + text; sufficient for DL
- Expertise: Team has CV/NLP specialists
- **Decision**: Ensemble of CNN (image) + BERT (text) classifiers

**Task C Constraints:**
- Real-time: <100ms latency requirement
- Scale: Millions of users; serving model must be fast
- Cold-start: New users have no history (collaborative filtering handles this)
- **Decision**: Collaborative filtering with optional DL for content-based fallback

---

**c) Decision Change Triggers [2 marks]**

**Task A change triggers:**
- If non-linear patterns discovered (e.g., exponential price growth in specific ZIP codes): Use DL
- If location data added as satellite imagery: Switch to CNN for image-based valuation
- If interpretability not required: Can scale to DL for marginal accuracy gains

**Task B change triggers:**
- If 10M+ labeled fraud images available: DL performance would justify complexity
- If real-time detection required (<500ms): Switch to lightweight ML with heuristics
- If fraud patterns simple and consistent: Rules sufficient (threshold-based detection)

**Task C change triggers:**
- If multi-modal data (images, descriptions, videos): DL embeddings better than CF
- If recommendations must explain why (e.g., "Similar to X"): Content-based ML with interpretability needed
- If cold-start problem critical: Use content-based DL to handle new properties

---

**d) Resources Estimate [1 mark]**

| Task | Data Needed | Timeline | ROI |
|------|------------|----------|-----|
| A | 100K samples ✓ ready | 2-3 months | $50K/year (time savings) |
| B | 500K images ready | 3-4 months | $200K/year (fraud prevention) |
| C | 2M interactions ready | 2-3 months | $150K/year (engagement boost) |

## Q2. When NOT to Use AI: Recognition of Over-Engineering [7 Marks]
[TYPE: Conceptual, Theoretical]

A logistics company considers using AI/ML for the following use cases. For each, identify whether AI is justified or if simpler solutions suffice.

a) **Delivery truck routing**: Determine optimal route for 50 stops across the city
   - Current: Manual assignment by dispatchers
   - Proposed: ML model learns optimal routes from historical delivery data
   - [1.5 marks] Decision + Justification

b) **Shipment damage detection**: Identify if packages are damaged upon arrival
   - Current: Manual inspection by warehouse staff
   - Proposed: Computer vision model on damage photos
   - [1.5 marks] Decision + Justification

c) **Employee attendance tracking**: Flag employees who may become "flight risks"
   - Current: HR manually reviews attendance records
   - Proposed: ML model predicts turnover based on attendance patterns
   - [2 marks] Decision + Justification (include ethical concerns)

d) **Truck fuel consumption monitoring**: Alert when vehicles consume more fuel than expected
   - Current: Dispatchers review monthly fuel reports
   - Proposed: Real-time ML model detects anomalies
   - [2 marks] Decision + Justification

**ANSWER:**

**a) Routing → Optimized Heuristics/OR, NOT ML [1.5 marks]**

**Decision: Use Operations Research (Vehicle Routing Problem solver), not ML**

Reasoning:
- **Well-defined problem**: VRP has established algorithms (Dijkstra, Christofides)
- **Deterministic rules work**: Distance, time windows, vehicle capacity are predictable
- **Why not ML**: No learning signal; routes change daily due to stops added/canceled
- **Better approach**: Use algorithms like OSRM (Open Source Routing Machine) or commercial solvers
- **When ML might help**: If incorporating real-time traffic, weather, driver behavior → hybrid approach

**Cost-Benefit**: Rule-based solution $10K, ML solution $100K + complexity. ROI favors rules.

---

**b) Damage Detection → Computer Vision ML, JUSTIFIED [1.5 marks]**

**Decision: Use CV model (justified)**

Reasoning:
- **Complex pattern**: Damage types varied (dents, tears, water damage); hard to encode as rules
- **High volume**: Manual inspection bottleneck; CV accelerates process
- **Clear signal**: Damage/no-damage clear outcome for training
- **Economic case**: Reduce inspection time by 70%, catch 95% of damage
- **Recommended**: CNN trained on 5K labeled damage/no-damage images

---

**c) Flight Risk Prediction → NOT ML (Ethical & Practical Issues) [2 marks]**

**Decision: Do NOT use ML; address root causes instead**

Reasoning:
- **Ethical concern**: Flagging "flight risks" may become self-fulfilling prophecy or discriminatory (unfairly targets certain groups)
- **Legal risk**: Using attendance data to predict turnover may violate privacy/labor laws
- **Practical**: Attendance != turnover cause; confuses signal with causation
- **Better approach**: 
  - Survey employees to understand dissatisfaction
  - Improve working conditions/pay (root cause)
  - Have career development conversations proactively
- **When ML appropriate**: AFTER improving root issues, use ML to identify engagement trends for targeted support (not prediction/punishment)

**Teaching point**: Not all business problems need ML; some need organizational change.

---

**d) Fuel Consumption Anomaly → Threshold Rules, NOT ML [2 marks]**

**Decision: Use rule-based alerting (threshold + baseline)**

Reasoning:
- **Simple problem**: Fuel consumption = Miles driven / MPG. Alert if significantly above expected.
- **Interpretability**: "Truck #42 consuming 15% more fuel than baseline" → clear action
- **Why not ML**: No complex patterns to learn; linear relationship dominates
- **Cost**: Rule-based solution trivial; ML overkill

**When ML justified**: If patterns include weather, driver behavior, road type, traffic → ML could extract complex interactions. But for simple anomaly detection, threshold rules sufficient.

**Rule logic**:
```
Expected_fuel = Distance / Historical_MPG
Actual_fuel = Fuel_used
If Actual > Expected * 1.15:  # 15% over baseline
  Alert: "Fuel efficiency degraded"
```

**Teaching point**: Measure twice, ML once. Start with rules; add ML only if ROI justifies complexity.

## Q3. AI Project Failure Diagnosis: Netflix Personalization Degradation [9 Marks]
[TYPE: Scenario-Based, Practical, Case Study]

Netflix's recommendation system (trained on 50 million viewing sessions) worked well for 6 months (engagement up 20%). Recently (last 2 months), user engagement and time-on-platform metrics declined 15%, despite model accuracy metrics remaining stable (prediction accuracy: 82%, similar to pre-decline baseline).

**Situation:**
- Same recommendation model deployed for 2 months without update
- Model accuracy hasn't degraded (82% precision maintained)
- But fewer users watching recommended content
- Watch-time declining despite recommendations being shown

Identify **at least 5 root causes** across the AI lifecycle and design a diagnostic framework.

a) [1 mark each = 5 marks] Identify 5 possible root causes for engagement decline despite stable accuracy

b) [2 marks] Design a monitoring dashboard to prevent this in the future

c) [2 marks] Outline remediation strategy

**ANSWER:**

**a) Five Root Causes (Accuracy ≠ Business Impact) [5 marks × 1 mark each]**

**Cause 1: Catalog Changes - Cold Start Problem**
- Netflix added 500 new original series in past 2 months
- Model trained on catalog from 6 months ago; lacks embeddings for new content
- Recommendations exclude new shows → users explore manually → less engagement with recommendations
- **Detection**: Compare recommendation coverage (% of recommendations from recent content vs. old)
- **Fix**: Retrain with new catalog; use content-based features for cold-start titles

**Cause 2: User Behavior Shift - Concept Drift**
- Holiday season ended; viewing patterns changed (less casual viewing, more intentional)
- Pre-trained model assumes old behavior distribution (weekend binge-watching)
- Recommendations optimized for old patterns; misaligned with current viewing intent
- **Detection**: Compare user demographics of engagers vs. non-engagers; segment analysis
- **Fix**: Retrain on recent 4 weeks of data; use seasonal features

**Cause 3: Feedback Loop / Echo Chamber**
- Model's recommendations drive what users watch → creates reinforcement loop
- Same users seeing same genres repeatedly → boredom/fatigue
- Model optimizes for short-term clicks but ignores diversity → long-term engagement suffers
- **Detection**: Analyze recommendation diversity (% same genre recommended repeatedly); user survey sentiment
- **Fix**: Add diversity constraint to recommendations (Explore vs. Exploit trade-off)

**Cause 4: Training-Serving Skew**
- Model trained on features computed in batch (yesterday's data)
- Features deployed in production use real-time data (current viewing trends)
- **Example**: Training used "Top genres last week" = [Drama, Comedy]. Production uses "Top genres now" = [Documentary, Sci-Fi]. Feature mismatch.
- **Detection**: Compare feature distributions between training and serving logs
- **Fix**: Synchronize feature computation; use same feature pipeline in both

**Cause 5: Interaction Data Quality Degradation**
- Partner content providers changed how they report viewing metrics (API change)
- User interactions corrupted or delayed by 24 hours (should be real-time)
- Model trained on clean data; deployed with degraded signal quality
- **Detection**: Check for missing values, latency spikes, duplicate events in serving logs
- **Fix**: Data quality gates; validate before model consumption

---

**b) Monitoring Dashboard to Prevent Future Decline [2 marks]**

**Key Metrics to Track:**

1. **Business Layer (Primary)**:
   - Engagement metrics: Watch-time per user, recommendations clicked, sessions started from recommendations
   - Revenue: Subscription retention, churn rate
   - **Threshold**: Alert if engagement drops >10% week-over-week

2. **Model Layer (Diagnostic)**:
   - Prediction accuracy: Precision, recall on held-out recent data
   - Recommendation diversity: % unique genres per user, Gini coefficient of recommendations
   - **Threshold**: Alert if diversity drops >20% (echo chamber sign)

3. **Data Layer (Early Warning)**:
   - Feature drift: Compare distributions of key features (top genres, user viewing history) between training and production
   - Data quality: % missing values, latency of user events, duplicate rows
   - **Threshold**: Alert if feature drift KL divergence >0.1

4. **Catalog Layer**:
   - New content coverage: % of recommendations from content added in last 30 days
   - Cold-start performance: Engagement on content <1 week old
   - **Threshold**: Alert if <30% recommendations from new content

5. **Feedback Loop Indicator**:
   - Recommendation repetition rate: Average time between similar recommendations to same user
   - User feedback sentiment: Survey: "Are recommendations surprising?" (want YES)
   - **Threshold**: Alert if >40% recommendations repeat within 7 days

---

**c) Remediation Strategy [2 marks]**

**Immediate (Week 1):**
1. Pause model updates; switch to previous model version if A/B test shows improvement
2. Increase exploration ratio: 70% exploitation (recommendations) + 30% exploration (random/diverse)
3. Analyze user complaints via support tickets for specific issues

**Short-term (Weeks 2-4):**
1. Retrain model on past 30 days of data only (remove stale patterns)
2. Add diversity constraint: Diversity score = -1 if recommending same genre as last 5 recommendations
3. Update catalog embeddings for content added in past 2 months
4. Implement A/B test: New model (with diversity) vs. old model; measure engagement

**Long-term (Month 2+):**
1. Establish automated retraining pipeline (weekly vs. monthly)
2. Implement real-time feature computation (reduce training-serving skew)
3. Build prediction → user action → outcome feedback loop (closed-loop metrics)
4. Add diversity, novelty, and serendipity objectives (not just accuracy)

**Expected improvement**: 10-15% engagement recovery within 4 weeks

## Q4. AI Marketplace Architecture Design: Building Internal AI Platform [10 Marks]
[TYPE: Scenario-Based, System Design]

A financial services company wants to build an **AI marketplace platform** (internal) where:
- **Data scientists** can publish models (fraud detection, credit risk, churn prediction)
- **Business teams** can discover and deploy models with one click
- **Governance teams** ensure compliance (audit trails, approval workflows)
- **Ops teams** manage infrastructure (scaling, monitoring, alerts)

Design the complete architecture with:

a) [2 marks] **Core components** (What subsystems needed?)
b) [2 marks] **Data flow** (How does a model move from development to production?)
c) [2 marks] **Security & governance** (Access control, audit, compliance)
d) [2 marks] **Failure handling** (What if model breaks in production?)
e) [2 marks] **Monitoring** (How do we track model health?)

**ANSWER:**

**a) Core Components [2 marks]**

**Platform Subsystems:**

1. **Model Registry**
   - Versioning of models (v1.0, v1.1, v2.0)
   - Metadata: Author, description, performance metrics, approval status
   - Artifact storage: Model binaries (pickle, ONNX, SavedModel)

2. **Feature Store**
   - Centralized feature definitions (customer_risk_score, transaction_velocity)
   - Feature versioning & lineage tracking
   - Shared feature computation (avoid redundant ETL)

3. **Model Serving Engine**
   - Low-latency inference (REST API, batch scoring)
   - Model routing (which version to serve, canary deployments)
   - Request/response logging

4. **Monitoring & Observability**
   - Model performance tracking (prediction distribution, accuracy drift)
   - Infrastructure monitoring (latency, throughput, error rates)
   - Alert system for anomalies

5. **Governance & Approval Workflow**
   - Request → Review → Approval → Deployment pipeline
   - Role-based access (Data Scientists: publish; Business: deploy; Compliance: approve)
   - Audit logging: Every action tracked with user, timestamp, reason

6. **Documentation & Discovery**
   - Model catalog (search models by use case)
   - Performance dashboards
   - Usage analytics (which models deployed, by whom)

---

**b) Data Flow: Model Lifecycle [2 marks]**

```
Step 1: Data Scientist Develops Model
├─ Trains on historical data
├─ Evaluates on holdout set (accuracy: 92%)
├─ Documents: Use case, features, assumptions, performance metrics
└─ Submits to Model Registry (Draft)

Step 2: Governance Review
├─ Compliance team reviews: Fairness, bias, regulatory alignment
├─ Flags issues: "Model has disparate impact on age < 25"
├─ Requests model card: Limitations, ethical considerations
└─ Approves if concerns addressed

Step 3: Staged Deployment
├─ Dev environment: Test integration with real-time data
├─ Staging environment: Run on historical data, compare to baseline
├─ Production (Canary): Deploy to 5% of transactions for 1 week
│  - Monitor accuracy, latency, drift
├─ Production (Full): If metrics stable, roll out 100%
└─ Model Registry: Mark as "Active"

Step 4: Monitoring & Maintenance
├─ Real-time dashboards: Track predictions, errors, latency
├─ Weekly reports: Model drift, business impact
├─ Trigger retraining if: Accuracy drops >5%, prediction distribution shifts
└─ Decommission: Archive old versions after 1 year

Step 5: User Access
├─ Business team discovers model in catalog
├─ Requests deployment (submits approval form)
├─ Governance team reviews business case
├─ Model automatically deployed to their environment
├─ Business gets API endpoint to call model
└─ Results logged to central audit system
```

---

**c) Security & Governance [2 marks]**

**Access Control (RBAC):**
```
Data Scientist:
  - Read all models
  - Publish new models (dev → staging)
  - View own models' performance

Business Team:
  - Discover models (filtered by use case)
  - Deploy approved models
  - Use via API (rate-limited)
  - Cannot see model internals

Compliance:
  - Approve/reject models
  - View audit logs
  - Run fairness checks
  - Can block deployment

Ops:
  - Manage infrastructure
  - Monitor serving health
  - Trigger rollbacks
  - View operational logs (not business data)
```

**Audit Trail:**
- All actions logged: Who, what, when, why
- Example: "Data Scientist A deployed Model v2.1 to staging at 2024-11-23 10:30 for fraud detection"
- Immutable log (cannot delete; can only append)
- Retained for 7 years (regulatory requirement)

**Compliance Checks:**
- Bias testing: Statistical parity, equalized odds across demographics
- Explainability: Model must pass interpretability score >0.7
- Performance baseline: Cannot degrade >5% from previous version
- Documentation: Model card, limitations, ethical review required

---

**d) Failure Handling [2 marks]**

**Failure Scenarios:**

1. **Model prediction fails** (e.g., NaN output due to missing feature)
   - Fallback: Return default decision (e.g., decline risky transaction) or previous model version
   - Alert: Notify ops team immediately
   - Mitigation: Input validation before model; feature store SLA

2. **Model accuracy degrades** (prediction drift detected)
   - Threshold: If accuracy drops >5% over 1 week
   - Action: Trigger automatic rollback to previous version
   - Alert: Notify data science team to investigate
   - Investigation: Check for data drift, concept drift, feedback loop

3. **High latency** (model takes >500ms to respond)
   - Fallback: Serve cached predictions if available
   - Action: Scale up serving replicas; check for resource contention
   - Alert: Notify ops team

4. **Data pipeline breaks** (feature store updates fail)
   - Impact: Models cannot serve without features
   - Fallback: Use stale features (cache layer) if recent unavailable
   - Recovery: Fix pipeline; validate data before serving
   - Alert: Governance team (compliance breach if SLA violated)

5. **Model poisoning** (bad data corrupts training)
   - Detection: Compare training data distribution to baseline
   - Prevention: Data quality gates before training
   - Recovery: Retrain on clean data; audit affected predictions
   - Accountability: Determine root cause; prevent recurrence

---

**e) Monitoring Dashboard [2 marks]**

**Real-time Metrics:**

```
1. Model Health
   ├─ Prediction latency (p50, p95, p99)
   │  Threshold: Alert if p99 > 500ms
   ├─ Error rate (NaN, timeout, exceptions)
   │  Threshold: Alert if > 1%
   ├─ Throughput (requests/second)
   │  Threshold: Alert if drops >20% from baseline
   └─ Model version deployed (which model currently live)

2. Prediction Quality
   ├─ Accuracy on recent validation set (recalculated daily)
   │  Threshold: Alert if drops >5%
   ├─ Prediction distribution shift (is distribution changing?)
   │  Metric: KL divergence of prediction distribution vs. training baseline
   │  Threshold: Alert if KL > 0.1
   ├─ Feature drift (are input features changing?)
   │  Metric: Statistical tests on feature distributions
   │  Threshold: Alert if significant shift detected
   └─ Calibration (are predicted probabilities well-calibrated?)
      Metric: Expected calibration error (ECE)
      Threshold: Alert if ECE > 0.05

3. Business Impact
   ├─ Models deployed (count, by team)
   ├─ Models producing results (% serving actively)
   ├─ Models awaiting approval (backlog)
   └─ Incidents (model rollbacks, emergency patches)

4. Infrastructure
   ├─ CPU/memory utilization
   ├─ Database query latency (feature store)
   ├─ Availability (% uptime, target: 99.9%)
   └─ Cost (per prediction, per model, per team)
```

## Q5. Data Quality Framework for Financial AI [8 Marks]
[TYPE: Practical, Implementation]

A bank ingests transaction data from 50 branches into a central data warehouse for ML model training. Data scientists report:
- "Models trained on January data perform well, but degrade in production on March data"
- "Some customer records have age = 999 years"
- "Transaction amounts sometimes negative without explanation"
- "Recent data has 40% missing income values vs. 2% six months ago"

a) [2 marks] **Define data quality dimensions** relevant to this scenario

b) [3 marks] **For each quality issue, design a check** (detection + remediation)

c) [2 marks] **Create a data quality SLA** (Service Level Agreement)

d) [1 mark] **Monitoring strategy** to prevent future issues

**ANSWER:**

**a) Data Quality Dimensions [2 marks]**

1. **Completeness**: % non-null values per field
   - Metric: (Non-null count / Total records) × 100
   - Target: >98% per field
   - Acceptable variation: ±2%

2. **Accuracy**: Values match expected range/format
   - Metric: % records passing validation rules
   - Target: >95% accurate
   - Example: Age in [18, 100], Transaction amount > 0

3. **Consistency**: Values aligned across systems/time
   - Metric: Matching records across branches (reconciliation)
   - Target: 100% reconciliation match
   - Example: Same customer ID in Branch A and central DB should have same demographics

4. **Timeliness**: Data arrives when needed
   - Metric: Latency (time from transaction to warehouse)
   - Target: <24 hours for batch; <5 minutes for real-time streams
   - Acceptable: 99th percentile latency <2 hours

5. **Uniqueness**: No duplicate records (or duplicates handled)
   - Metric: Duplicate record count
   - Target: <0.1% duplicates (expected some retransmissions)
   - Action: Deduplicate using transaction ID + timestamp

6. **Validity**: Values match defined schema
   - Metric: Schema validation (data type, length checks)
   - Target: 100% valid schema
   - Example: Age must be integer, Income must be numeric

---

**b) Quality Checks & Remediation [3 marks]**

**Issue 1: Age = 999 (Invalid values)**

Detection:
```python
invalid_age = data[data['Age'].isin([999, -1, 0]) | (data['Age'] > 120)]
if len(invalid_age) > 0.5% of total:  # Threshold
    Alert: "Invalid age values detected in {branch}"
```

Remediation (Priority order):
1. Flag: Mark as "Invalid - review required"
2. If >50% of transaction: Stop processing, escalate to data team
3. If <50%: 
   - Option A: Impute with median/mode (risky for modeling)
   - Option B: Exclude from model training
   - Option C: Fill from alternative data source (ID verification)
4. Prevent: Add check at data ingestion point

**Issue 2: Negative transaction amounts (Without explanation)**

Detection:
```python
negative_transactions = data[data['Amount'] < 0]
% negative = len(negative_transactions) / len(data)

# Expected: Some negatives (refunds), but should be ~1-3%
if % negative > 5%:
    Alert: "Unusually high negative transaction rate"
```

Root cause analysis:
- Check if branch recently changed processing system
- Verify: Are negatives marked as refunds/reversals in separate flag?
- Investigate: Did data extraction lose the transaction type?

Remediation:
1. Add field: `transaction_type` (Debit/Credit/Refund/Reversal)
2. For modeling: 
   - Separate negative transactions (refunds) for analysis
   - Train model only on primary transactions (Amount > 0)
   - Or: Include `transaction_type` as feature
3. Prevent: Validate at ingestion; reject Amount < 0 without matching reversal flag

**Issue 3: Missing income values increased from 2% to 40%**

Detection:
```python
missing_rate = data['Income'].isnull().sum() / len(data)

# Track over time
if missing_rate > 2% * 1.5:  # Allow 50% increase as threshold
    Alert: "Missing income rate jumped to {missing_rate}%"
    If missing_rate > 10%:
        Alert Severity: CRITICAL
```

Root cause investigation:
- Changed data source? (New branch system might not capture income)
- API change? (Partner income verification service offline?)
- Policy change? (New branches don't collect income?)
- Data engineering error? (Null handling changed in ETL?)

Remediation:
1. Short-term: Investigate root cause (contact branches/systems team)
2. Medium-term: 
   - Impute missing income using statistical methods (KNN, regression)
   - Or use alternative income proxy (savings account balance, credit limit)
3. Long-term: 
   - Enforce income collection at all branches
   - Add data quality SLA to branch systems
   - Automate alerting on missing rate changes >20%

**Issue 4: Model performance degradation (Jan → Mar)**

Detection:
```
# Monitor model accuracy over time
jan_accuracy = 0.92  # Training data
mar_accuracy = 0.78  # Production data
if mar_accuracy < jan_accuracy - 0.10:  # 10% drop
    Alert: CONCEPT DRIFT or DATA DRIFT detected
```

Root cause investigation:
- **Data drift**: Distribution of input features changed (income dropped, age distribution shifted)
  - Check: Compare feature distributions Jan vs. Mar
  - If confirmed: Retrain model on recent data
  
- **Concept drift**: Underlying relationship changed (customers behaving differently)
  - Check: Are labels changing? (more defaults, different transaction patterns)
  - If confirmed: Business has changed; model no longer fits

- **Data quality degradation**: New data quality issues introduced
  - Check: Is Mar data quality lower than Jan?
  - Likely culprit: 40% missing income issue (causes feature corruption)

Remediation:
1. Retrain model on Mar data with clean features
2. If quality issues found: Fix data pipeline first, then retrain
3. Implement production monitoring (track prediction distribution, accuracy drift)
4. Set up automatic retraining trigger (if drift detected)

---

**c) Data Quality SLA (Service Level Agreement) [2 marks]**

```
SERVICE LEVEL AGREEMENT - Financial Data Quality
Effective: 2024-Q4
Parties: Branch Operations, Central Data Team, ML Platform

COMMITMENT METRICS:
┌────────────────────────────────────────────┐
│ Metric               │ Target  │ Frequency │
├─────────────────────────────────────────────┤
│ Completeness         │ ≥98%    │ Daily     │
│ Validity             │ ≥99%    │ Daily     │
│ Timeliness           │ <24hrs  │ Daily     │
│ Uniqueness (dupes)   │ <0.1%   │ Daily     │
│ Reconciliation       │ 100%    │ Weekly    │
│ Accuracy             │ ≥95%    │ Weekly    │
└────────────────────────────────────────────┘

CONSEQUENCES FOR VIOLATIONS:

Level 1 (Warning): Metric dips 5-10% below target
├─ Action: Alert sent; Root cause investigation within 24 hours
├─ Owner: Data team
└─ No penalties; informational

Level 2 (Critical): Metric dips >10% below target
├─ Action: Halt new model deployments; focus on data quality fix
├─ Timeline: Resolution required within 48 hours
├─ Owner: Data team + Branch leadership
└─ Penalty: (if SLA not met) ML budget reduced 10%

Level 3 (Severe): Quality not restored within 48 hours
```

## Q6. Feature Engineering for Customer Lifetime Value (CLV) Prediction [9 Marks]
[TYPE: Practical, Implementation Focus]

An e-commerce company wants to predict which customers will generate >$10,000 revenue over 3 years (high-value customers). Current data:

```
Customer Profile: ID, Age, Gender, Signup_Date, Country
Order History: Order_ID, Amount, Date, Category, Payment_Method, Returned (Y/N)
Engagement: Last_Login_Date, Pages_Visited_Last_7_Days, Email_Opens, etc.
```

**Task:**
a) [3 marks] Design 12 meaningful features for CLV prediction. For each:
   - Feature name & calculation
   - Business relevance (why predicts CLV)
   - Potential data leakage?

b) [2 marks] Identify feature interactions (non-obvious combinations)

c) [2 marks] Handle special cases: New customers, sparse data, missing values

d) [2 marks] Feature validation approach

**ANSWER:**

**a) 12 Key Features for CLV Prediction [3 marks × 4 features per row]**

**Row 1: Recency, Frequency, Monetary (RFM) - Classical Features**

1. **Recency (days since last purchase)**
   - Calculation: TODAY() - MAX(Order_Date) for each customer
   - Relevance: Recent customers more likely to spend more in next 3 years; inactive customers unlikely
   - Leakage risk: NONE (available at any point in time)
   - Domain: "Active customer signal"

2. **Frequency (purchase count last 12 months)**
   - Calculation: COUNT(Orders) where Order_Date ∈ last 365 days
   - Relevance: Repeat customers have higher CLV than one-time buyers
   - Leakage risk: NONE (historical, before prediction window)
   - Domain: "Loyalty indicator"

3. **Monetary (average order value)**
   - Calculation: AVG(Order_Amount) for all historical orders
   - Relevance: Customers with high AOV likely to continue spending
   - Leakage risk: NONE (but update regularly)
   - Domain: "Spending power"

4. **Customer Tenure (days since signup)**
   - Calculation: TODAY() - Signup_Date
   - Relevance: Long-term customers more stable; churn risk lower
   - Leakage risk: NONE (known at signup)
   - Domain: "Relationship duration"

---

**Row 2: Behavioral Features - Engagement & Activity**

5. **Average Session Length (engagement indicator)**
   - Calculation: AVG(Pages_Visited_Last_30_Days / Days_Active)
   - Relevance: Higher engagement correlates with intent to purchase
   - Leakage risk: NONE (lagged by 30 days; backward-looking)
   - Domain: "Purchase intent"

6. **Email Engagement Rate**
   - Calculation: (Email_Opens / Email_Sent) × 100
   - Relevance: Responsive customers more likely to convert marketing efforts into sales
   - Leakage risk: NONE (only uses historical email opens)
   - Domain: "Marketing responsiveness"

7. **Category Diversity (how many categories ordered from)**
   - Calculation: COUNT(DISTINCT Category) across all orders
   - Relevance: Diverse purchases indicate exploration; broader tastes = higher lifetime value
   - Leakage risk: NONE (historical)
   - Domain: "Cross-selling opportunity"

8. **Device Diversity (mobile, desktop, tablet)**
   - Calculation: COUNT(DISTINCT Device_Type) used by customer
   - Relevance: Multi-device users more engaged; likely higher CLV
   - Leakage risk: NONE
   - Domain: "Device adoption"

---

**Row 3: Quality & Satisfaction Signals**

9. **Return Rate (product satisfaction proxy)**
   - Calculation: (Orders_Returned / Total_Orders) × 100
   - Relevance: High return rate = dissatisfaction; negative signal for CLV
   - Leakage risk: NONE (historical returns before prediction)
   - Domain: "Customer satisfaction"

10. **Average Review Rating (if available)**
    - Calculation: AVG(Rating) for products this customer reviewed
    - Relevance: Customers leaving positive reviews likely satisfied; repeat buyers
    - Leakage risk: NONE (lagged reviews)
    - Domain: "Satisfaction metric"

11. **Payment Method Diversity**
    - Calculation: COUNT(DISTINCT Payment_Method) used
    - Relevance: Customers trying multiple payment methods comfortable with platform
    - Leakage risk: NONE
    - Domain: "Platform trust"

12. **Seasonal Purchase Consistency**
    - Calculation: STD(Order_Amount) across quarters; or Coefficient of Variation
    - Relevance: Consistent spending = predictable CLV; erratic = risky
    - Leakage risk: NONE (historical pattern)
    - Domain: "Purchase predictability"

---

**b) Feature Interactions (Non-obvious Combinations) [2 marks]**

**High-value interactions:**

1. **Recency × Frequency interaction**
   - Formula: Frequency / (Recency + 1)
   - Intuition: Recent + frequent = high intent; Recent + infrequent = risky
   - Example: Customer A: Frequency=5, Recency=10 days → Score = 5/11 = 0.45 (high intent)
            Customer B: Frequency=5, Recency=200 days → Score = 5/201 = 0.02 (dormant)

2. **Monetary × Category Diversity**
   - Formula: AOV × Category_Diversity
   - Intuition: High spender across many categories = strong CLV signal
   - Example: Customer spending $100 avg across 10 categories = 1000 score (high)
            Customer spending $100 in 1 category = 100 score (lower)

3. **Tenure × Return Rate**
   - Formula: Tenure_Years / (1 + Return_Rate%)
   - Intuition: Long-term customers with low returns = loyal high-CLV segment
   - Example: 5-year customer with 2% returns = 5/1.02 ≈ 4.9 (excellent)
            New customer with 30% returns = 0.5/1.30 ≈ 0.38 (risky)

4. **Engagement × Seasonality (Consistency)**
   - Formula: Session_Length × (1 / Spending_StdDev)
   - Intuition: Engaged customers with predictable spending = model-friendly, stable CLV
   - Example: High engagement (10 pages/day) + low variation = strong signal

5. **Email Engagement × Category Diversity**
   - Formula: Email_Open_Rate × Category_Diversity
   - Intuition: Responsive to emails AND buys diverse items = strong marketing potential
   - Insight: Segments for targeted campaigns

**c) Handling Special Cases [2 marks]**

**Case 1: New Customers (zero historical data)**

Problem: RFM features undefined; no order history
Solution:
```
Approach A: Profile-based proxy features
  - Age, Country → Look up average CLV for similar demographics
  - Device type → Desktop users historically higher CLV than mobile
  - Signup source → Users from paid ads vs. organic have different CLV

Approach B: First-order signals
  - First order amount: Higher first order → higher CLV tendency
  - Time to first purchase: Fast converters → higher CLV
  - First category chosen: Luxury vs. basic indicates spending power

Approach C: Fallback strategy
  - Use population baseline (average CLV) for new customers
  - As customer accumulates orders, transition to personalized prediction
  - Set model confidence = LOW for new customers
```

**Case 2: Sparse Data (customers with 1-2 orders)**

Problem: Statistics unstable; RFM incomplete
Solution:
```
Approach: Weighted features
  - Frequency: Use (Orders_Count + 1) in denominator to reduce noise
  - Monetary: Regularize towards population mean if <5 orders
    Avg = (Customer_AOV * Orders_Count + Population_Mean * 2) / (Orders_Count + 2)
  - Return Rate: Don't penalize heavily if <5 orders (small sample)
    Use Beta distribution with weak prior instead of raw %
```

**Case 3: Missing Values**

Problem: Some fields null (Email_Opens, Reviews, etc.)
Solution:
```
Approach A: Domain-specific imputation
  - Missing Email_Opens: Assume ZERO (customer never received/opened)
  - Missing Reviews: Assume median (lazy customers)
  - Missing Category: Use dominant category

Approach B: Indicator variable
  - Create Feature: "is_Email_Data_Missing" (Y/N)
  - Insight: Missingness itself may be signal (opted out of emails)
  - Impute: Use population mean for primary feature

Approach C: Model handles naturally
  - Tree-based models (XGBoost) handle missing values natively
  - Create "unknown" category for categorical missing
```

**d) Feature Validation Approach [2 marks]**

**Validation Steps:**

```
Step 1: Statistical Validation
├─ Check distributions for each feature
├─ Visualize: Histogram, boxplot (look for outliers)
├─ Test: Correlation with target (CLV >$10K)
│  Feature-Target correlation should be >0.1 (meaningful signal)
└─ Remove: Features with <0.05 correlation (noise)

Step 2: Business Validation
├─ Ask domain expert: "Does this feature make business sense?"
├─ Example: Recency should negatively correlate with CLV (✓ passes)
│           Return_Rate should negatively correlate (✓ passes)
│           Device_Diversity unclear (? requires discussion)
└─ Adjust: Drop features that fail business logic

Step 3: Leakage Detection
├─ Question: "Could this feature be known at prediction time?"
├─ Timeline: Feature must be computable BEFORE 3-year prediction window
├─ Example: Future_Returns = LEAKAGE (future outcome)
│           Past_Returns = OK (historical)
└─ Remove: Any suspected leakage features

Step 4: Stability Testing
├─ Split data: Train on 2022 customers; test on 2023 customers
├─ Requirement: Feature distributions similar (no shift)
├─ Check: Does feature ranking change between train/test?
│   If yes → feature unstable, may hurt generalization
└─ Adjust: Drop unstable features or add temporal regularization

Step 5: Multicollinearity Check
├─ Compute: Correlation matrix of all features
├─ Rule: If Corr(Feature_A, Feature_B) > 0.9 → keep only one
├─ Reason: Redundant features confuse tree models; increase variance
└─ Action: Remove highly correlated pairs (keep one per pair)

Step 6: Outlier Handling
├─ Define outliers: Values >3 std from mean
├─ Options:
│  A) Cap at 95th percentile (winsorize)
│  B) Remove records with outliers
│  C) Log-transform (reduce impact)
└─ Decision: Use capping for Monetary; removal for Recency anomalies

Final Validation Dataset:
├─ 12 features → Post-validation: ~8-10 features (dropped redundant/noisy)
├─ Performance: Train model on validated features
├─ Metric: AUC on holdout test set (target >0.75)
└─ Sign-off: Data scientist + business stakeholder approval
```

A ride-sharing company needs features for real-time driver allocation. ML model must rank drivers by likelihood of accepting a ride request within 30 seconds. Features needed:

Design a **Feature Store** architecture:

```
                   │ (Must respond in <30 seconds)

        ┌─────────────────────┐
        │ Feature Store Query │
        │  (Online Layer)     │
        └────────┬────────────┘
                 │
     ┌───────────┼───────────┐
     ▼           ▼           ▼
 [Redis]    [DynamoDB]  [Memcached]
  Cache      (Hot)      (Availability)
   │           │            │
   │ ◄─────────┼────────────┤
   │ Driver    │ Location   │ Rating
   │ Acept %   │ (Real-time)│ (Daily)
```

**Rationale:**

**c) Latency Optimization Strategies [2 marks]**

**Current bottleneck**: 5 seconds (exceeds 30-second SLA)

**Optimization 1: Pre-compute & Cache (Biggest win)**
- Pre-compute driver acceptance rate → Redis (lookup <10ms vs. 500ms DB query)

- Expected improvement: 500ms query time → 10ms cache = 50× speedup

**Optimization 2: Parallel Feature Fetching**
- Fetch acceptance rate + rating + location simultaneously (not sequential)
- Using async/await:
  ```
  Parallel:
    - Query Redis (acceptance) = 10ms
    - Query Redis (rating) = 10ms
    - Fetch GPS (location) = 50ms
  Total: 50ms (not 10+10+50=70ms sequential)
  ```

**Optimization 3: Local Model Serving**
- ML model runs on-device or edge server (not central API)
- Reduces network round-trip from 100ms to 10ms

**Optimization 4: Prune Feature Set**
- Use only top-5 most impactful features (not all 7)
- Reduces computation + data transfer time

**Optimization 5: Approximate Features**
- Use stale location (5 minutes old) instead of live GPS
- Trade: 5-second savings for 5-minute staleness (acceptable for driver ranking)
- Real-time precision not critical; 5-min-old location 95% accurate for ranking

**Resulting latency budget:**
```
Feature Fetching:        50ms  (parallel Redis + GPS)
Model Inference:         20ms  (small model locally)
API Overhead:            10ms
Buffer:                  20ms
─────────────────────────────
Total:                  100ms (well within 30-second SLA)
```

## Q8. Learning System Selection for Autonomous Vehicles [9 Marks]
[TYPE: Scenario-Based, Learning Mechanism Selection]

An autonomous vehicle company needs to decide learning mechanisms for three sub-systems:

**Problem A**: Lane Detection (staying in lane)

- Latency requirement: <50ms decision
- Safety: Critical (dangerous if wrong)

**Problem B**: Pedestrian Behavior Prediction (will pedestrian cross street?)
- Input: Pedestrian position, speed, direction + scene context
- Output: Probability pedestrian crosses within 5 seconds
- Data: 10,000 video hours with pedestrian annotations
- Latency: <100ms
- Safety: Critical (need to brake preemptively)

**Problem C**: Route Optimization (best route to destination?)
- Input: Current location, destination, real-time traffic data
- Output: Recommended next road/turn
- Data: Historical driving routes, current traffic conditions
- Latency: <1 second (can wait)
- Safety: Non-critical (can suggest; user can override)

For each problem:
a) [2 marks] Select learning mechanism (Supervised, Unsupervised, Reinforcement, or Hybrid)
b) [2 marks] Justify selection with problem-specific constraints

**ANSWER:**

**Problem A: Lane Detection → Supervised Learning (Deep Learning) [5 marks]**

**Justification [2 marks]:**

1. **Clear target variable**: Lane markings (ground truth) explicitly labeled in training data
2. **Abundant labeled data**: 100,000 video hours = millions of image frames with annotations
3. **Well-studied problem**: Lane detection = image segmentation (solved with CNNs)
4. **Deterministic task**: Given image, lane location is objective (not ambiguous like navigation)
5. **Why not other mechanisms**:
   - **Unsupervised**: Lane markings are defined entities; not clustering/discovery problem
   - **Reinforcement**: Not sequential decision-making; single image → single decision
   - **Hybrid**: Not needed; pure supervised sufficient

**Implementation Details [1 mark]:**

```
Architecture: ResNet-50 or YOLOv8 for lane segmentation
Training:
  - Dataset: 100K hours = ~3M frames (at 30 fps)
  - Split: 70% train, 15% val, 15% test
  - Loss function: Semantic segmentation loss (IoU/Dice)
  - Validation: Accuracy >95% on test set

Deployment:
  - Model: TensorFlow Lite or ONNX (mobile/edge optimization)
  - Latency: <50ms on embedded GPU (NVIDIA Jetson)
  - Confidence threshold: Output steering only if confidence >90%
```

**Failure Handling [1 mark]:**

```
Failure scenarios:
1. Lane unclear (rain, snow, faded markings)
   → Fallback: Use previous steering angle (momentum)
   → Alert: Reduce speed automatically

2. Model produces invalid angle (>30° or NaN)
   → Clamp: Force valid range [-30°, +30°]
   → Log: Alert sensor/model team

3. Model latency exceeds 50ms
   → Use cached prediction from previous frame
   → Degrade gracefully (safe, but less accurate)

4. High uncertainty (confidence <70%)
   → Trigger manual control request
   → Warning: "Take over steering"
```

**Problem B: Pedestrian Behavior Prediction → Supervised Learning (Classification) [5 marks]**

**Learning Mechanism: Supervised Classification**

**Justification [2 marks]:**

1. **Clear binary target**: Pedestrian crosses / doesn't cross (observable outcome)
2. **Historical labels**: 10,000 hours of video with pedestrian annotations + ground truth (did they cross?)
3. **Bounded prediction window**: 5-second prediction horizon makes problem tractable
4. **Why supervised**:
   - Clear ground truth (video shows actual behavior)
   - Abundant training data
   - Classification task (binary or multi-class: crosses soon, crosses late, doesn't cross)

5. **Why not other mechanisms**:
   - **Unsupervised**: Clustering pedestrians not useful; need prediction
   - **Reinforcement**: Could frame as sequential (predict next frame position), but supervised + RNN more direct
   - **Semi-supervised**: Would only help if limited labels; we have 10K hours

**Implementation Details [1 mark]:**

```
Features (hand-engineered or learned):
  - Pedestrian position (x, y, distance from car)
  - Pedestrian velocity vector (direction, speed)
  - Pedestrian gaze direction (facing toward road?)
  - Scene context (urban, highway, school zone)
  - Time of day, weather
  - Road markings, traffic lights

Model: Gradient Boosting (XGBoost) or LSTM (for temporal sequence)
  - Input: Pedestrian trajectory last 1 second + scene
  - Output: P(crosses within 5 seconds)
  - Accuracy target: >90% (minimize false negatives)

Training:
  - Dataset: 10K hours = ~1M pedestrian frames
  - Balance: Crosses=10%, Doesn't cross=90% (imbalanced)
  - Use SMOTE or class weights to handle imbalance
  - Metric: Focus on recall (minimize missed crossings)
```

**Failure Handling [1 mark]:**

```
1. Model uncertain (probability 40-60%)
   → Conservative: Assume pedestrian will cross
   → Action: Pre-brake preparation

2. Pedestrian behavior anomalous (sudden speed change)
   → Flag: "Unexpected behavior"
   → Action: Reduce speed automatically

3. Latency exceeds 100ms
   → Use cached prediction
   → Fallback: Assume worst case (pedestrian will cross)

4. Model drifts (pedestrian types in test set different from training)
   → Continuous monitoring for performance decay
   → Trigger retraining if accuracy drops >5%
```

**Problem C: Route Optimization → Reinforcement Learning (or Planning Algorithm) [5 marks]**

**Learning Mechanism: Reinforcement Learning (or Hybrid with Optimization)**

**Justification [2 marks]:**

1. **Sequential decision-making**: Each turn → next road → next turn (not single decision)
2. **Reward signal available**: Route completion time, distance, comfort (minimize bumps)
3. **Exploration-exploitation tradeoff**: Learn best routes while respecting real-time constraints
4. **Why not supervised**:
   - No pre-labeled optimal path; routes depend on live traffic (constantly changing)
   - Future traffic state unknown at training time
   - Multiple valid paths (not single ground truth)

5. **Why not unsupervised**:
   - Not clustering problem; need optimization

6. **Why RL**:
   - Agent learns policy: state (location, traffic) → action (which road next)
   - Reward: Reach destination fast, comfortable drive
   - Adapts to new traffic patterns (not fixed routes)

**Implementation Details [1 mark]:**

```
RL Framework: Q-Learning or Policy Gradient
  - State: (current_location, destination, traffic_conditions)
  - Action: Choose next road/turn (from 2-5 options typically)
  - Reward: 
    * +10: Reach destination
    * -1: Each turn (encourage directness)
    * -5: Congested road (avoid traffic)
    * -2: Long detour (prefer efficiency)

Training:
  - Experience: Historical routes + real-time traffic updates
  - Learn: Policy π(state) → action
  - Deploy: Use learned policy for route suggestions

Optimization hybrid:
  - If live traffic data available: Use Google Maps API (OR solver)
  - If live data unavailable: Use learned RL policy (falls back gracefully)
```

**Failure Handling [1 mark]:**

```
1. Route becomes invalid (construction, closed road)
   → Trigger replanning immediately
   → Use fallback: Google Maps suggestions

2. Predicted traffic inaccurate
   → Continuous monitoring
   → Update model if ETA error >15 minutes

3. User prefers different route (scenic vs. fast)
   → Adapt reward function
   → RL learns personalized policy

4. RL model performs worse than baseline
   → Evaluate: Why (insufficient training, distribution shift)?
   → Fallback: Use deterministic optimization algorithm
   → Retry RL with more data/better reward shaping
```

## Q9. Transfer Learning for Medical Image Classification [10 Marks]
[TYPE: Scenario-Based, Advanced]

A hospital wants to classify X-ray images into three categories: Normal, Pneumonia, COVID-19. Available resources:

**Data Scenario 1**: 1,000 labeled COVID-19 X-rays (scarce)
**Data Scenario 2**: 10,000 labeled general pneumonia X-rays
**Data Scenario 3**: 100,000 ImageNet pretrained weights available

**Task**: Design transfer learning strategies for each scenario

a) [2 marks] Scenario 1 (1K COVID images only)
b) [2 marks] Scenario 2 (10K pneumonia images)
c) [2 marks] Scenario 3 (100K general X-ray images available, then COVID)
d) [2 marks] Trade-offs: Which approach maximizes accuracy with minimal computational cost?
e) [2 marks] Validation strategy for transfer learning

**ANSWER:**

**a) Scenario 1: 1,000 COVID-19 Images Only [2 marks]**

**Transfer Learning Strategy: ImageNet Pretrain → Fine-tune Minimal Layers**

**Problem**: 1K images far too few to train from scratch (ResNet-50 needs millions)

**Solution**:
```
Step 1: Start with ImageNet-pretrained ResNet-50
        (Trained on 1.2M images, millions of parameters learned)

Step 2: Freeze most layers (keep ImageNet knowledge)
        └─ Freeze: Layers 1-3 of ResNet (early feature detectors)
        └─ Unfreeze: Layer 4 + classification head (medical-specific)

Step 3: Fine-tune with low learning rates
        ├─ Layer 4 learning rate: 0.0001 (10× lower than training)
        ├─ Classifier head learning rate: 0.001 (100× lower)
        └─ Reason: Preserve pretrained weights; small updates only

Step 4: Data augmentation (critical with small dataset)
        ├─ Rotations: ±15°
        ├─ Zooms: 0.9-1.1×
        ├─ Flips: Horizontal
        ├─ Brightness/contrast variations
        └─ Purpose: Artificially expand 1K → 10K+ effective samples

Step 5: Regularization to prevent overfitting
        ├─ Dropout: 0.5 (drop 50% of neurons)
        ├─ L2 regularization: λ=0.0001
        ├─ Early stopping: Stop if validation accuracy plateaus
        └─ Expected performance: 85-90% accuracy (acceptable for 1K images)

Training Config:
├─ Batch size: 32 (small, to stabilize gradients)
├─ Epochs: 50-100 (with early stopping)
├─ Validation split: 20% (200 images for validation)
├─ Test set: Separate 200 images (hold out before training)
└─ Expected training time: 1-2 hours (single GPU)
```

**Expected Performance**: 85-90% accuracy (limitation: small dataset)

**b) Scenario 2: 10,000 Pneumonia X-rays [2 marks]**

**Transfer Learning Strategy: Deeper Fine-tuning + Domain Adaptation**

**Rationale**: 10K images sufficient for more aggressive fine-tuning than Scenario 1

**Solution**:
```
Step 1: ImageNet pretrain → More layers to unfreeze
        ├─ Freeze: Layers 1-2 (early edge/texture detectors - general)
        ├─ Unfreeze: Layers 3-4 + classification head (medical-specific)
        └─ Reasoning: Layer 3-4 learn mid/high-level features relevant to diseases

Step 2: Progressive unfreezing (avoid catastrophic forgetting)
        ├─ Week 1: Fine-tune only classifier head
        │          (learning rate: 0.001, accuracy reaches 88%)
        ├─ Week 2: Unfreeze Layer 4 (lower learning rate: 0.0001)
        │          (accuracy improves to 91%)
        └─ Week 3: Optional unfreeze Layer 3 if still improving
                   (diminishing returns expected)

Step 3: Domain adaptation techniques
        ├─ Class imbalance handling: Pneumonia vs. Normal ratio?
        │   - Use class weights if imbalanced
        ├─ Style transfer: X-ray images stylistically different from ImageNet
        │   - Apply histogram equalization (normalize X-ray appearance)
        └─ Feature extraction + classifier approach (simpler alternative)

Step 4: Regularization (less aggressive than Scenario 1)
        ├─ Dropout: 0.3 (more data = less overfitting risk)
        ├─ L2 regularization: λ=0.00001 (lighter)
        └─ Early stopping: If validation plateau for 10 epochs

Step 5: Data split & evaluation
        ├─ Train: 70% (7,000 images)
        ├─ Validation: 15% (1,500 images)
        ├─ Test: 15% (1,500 images)
        └─ Expected accuracy: 91-94%
```

**Expected Performance**: 91-94% accuracy

```
        ├─ Dataset: 1,000 COVID images
        ├─ Learning rates:
        │  - Frozen layers 1-3: 0.0 (never update)
        │  - Layer 4: 0.00001 (minimal update, preserve X-ray knowledge)
        │  - Classifier head: 0.0001

Step 4: Comparison of transfer paths
```

## Q10. Model Evaluation Framework: Bank Loan Default Prediction [10 Marks]

A bank deploys a loan default prediction model (binary classification: Default/No-default). Model performs as follows on 1,000 test loans:

```
Predicted No-Default: 650 loans

Actual outcomes:

├─ False Positives (FP):  70 (predicted default, actually paid)
├─ True Negatives (TN):   630 (correctly predicted no-default)
└─ False Negatives (FN):  20 (predicted no-default, actually defaulted)
```

**Evaluation tasks:**

a) [2 marks] **Calculate 6 evaluation metrics** (Accuracy, Precision, Recall, F1, ROC-AUC, Specificity)

c) [2 marks] **Threshold optimization** (adjust decision threshold to maximize profit)

**ANSWER:**

**a) Calculate 6 Evaluation Metrics [2 marks]**

**Confusion Matrix**:
```
                 Predicted
                Default  No-Default
Actual  Default   TP=280   FN=20      (Total Defaults: 300)
        No-Def   FP=70    TN=630      (Total No-Def: 700)
                 (350)    (650)
```

**Metric 1: Accuracy**
```
Accuracy = (TP + TN) / Total
         = (280 + 630) / 1000
         = 910 / 1000
         = 0.91 or 91%

Interpretation: Model correct 91% of time (high, but misleading metric for imbalanced classes)
Caveat: 70% base rate (700 non-defaults) → 70% accuracy if always predict "No-default"
```

**Metric 2: Precision (Positive Predictive Value)**
```
Precision = TP / (TP + FP)
          = 280 / (280 + 70)
          = 280 / 350
          = 0.80 or 80%

Interpretation: Of 350 loans predicted as default, 80% actually defaulted
              → 20% false alarm rate (unnecessary loan denials)
Business meaning: "If I deny a loan based on this model, 80% chance I'm right"
```

**Metric 3: Recall (Sensitivity / True Positive Rate)**
```
Recall = TP / (TP + FN)
       = 280 / (280 + 20)
       = 280 / 300
       = 0.933 or 93.3%

Interpretation: Captured 93.3% of actual defaulters
              → Missed only 20 out of 300 defaults
Business meaning: "Of all loans that will default, model catches 93.3%"
Implications: Excellent at catching risk (safe for bank)
```

**Metric 4: F1-Score (Harmonic mean of Precision & Recall)**
```
F1 = 2 × (Precision × Recall) / (Precision + Recall)
   = 2 × (0.80 × 0.933) / (0.80 + 0.933)
   = 2 × (0.746) / (1.733)
   = 1.493 / 1.733
   = 0.861 or 86.1%

Interpretation: Balanced measure of model performance (good if precision-recall tradeoff important)
```

**Metric 5: Specificity (True Negative Rate)**
```
Specificity = TN / (TN + FP)
            = 630 / (630 + 70)
            = 630 / 700
            = 0.90 or 90%

Interpretation: Of 700 loans that won't default, model correctly approves 90%
              → 10% wrongly denied (customers lost)
```

**Metric 6: ROC-AUC (Area Under Receiver Operating Characteristic Curve)**
```
Calculation requires probability scores (not just binary predictions)
Assuming probabilities available:

ROC-AUC interpretation:
├─ 0.5: Random classifier (coin flip)
├─ 0.70-0.80: Acceptable discrimination
├─ 0.80-0.90: Excellent discrimination
├─ >0.90: Outstanding

Estimated for this model: ~0.92 (based on high TP rate + low FN)
(Derivation would need actual probability scores, not just binary predictions)
```

```
      └─ Impact: May shift feature distributions

├─ Level 1 (Warning): Metric dips 5-10% → Investigation required
├─ Level 2 (Critical): Metric dips >10% → Halt new deployments; retrain
```

**Retraining Trigger**:

```
Automatic retraining if any condition met:
├─ Recall drops below 90%

├─ Collect recent labeled data (loans from past 6 months with known outcomes)
```

## Q11. Rule-Based vs ML Trade-off: Bank Transaction Flagging [7 Marks]
[TYPE: Practical Decision]

A bank wants to flag suspicious transactions for manual review. They have:
- 50 million transactions/day
- Current rules: "Flag if amount > $10K OR customer made withdrawal at 3 AM"
- Flagging rate: ~5% (500K transactions/day for review)

They want to reduce manual review workload. Options:
a) Add more rules (tighter thresholds)
b) Deploy ML model (trained on fraud labels)

Question: Evaluate each approach. What would you recommend? Why? [7 marks]

**ANSWER:**

**Option A: Add More Rules [1.5 marks]**
```
Approach: IF amount > $10K AND country != registered_country 
              AND time between 11 PM - 7 AM
              AND first use of card
          THEN flag
Outcome: Flagging rate drops from 5% → 2% (100K transactions)
Pros:
  - Fully explainable (compliance happy)
  - Zero latency (rule evaluation: <1ms)
  - No model training/maintenance
Cons:
  - Rules become fragile; need constant tuning
  - Miss new fraud patterns
  - False negatives accumulate (fraudsters adapt)
  - 2% still means 100K reviews/day (high workload)
```

**Option B: ML Model [1.5 marks]**
```
Approach: Train classifier on fraud labels (fraud/non-fraud)
Input: Transaction features (amount, location, time, merchant, velocity)
Output: Probability of fraud
Decision: Flag if P(fraud) > threshold (tuned for precision/recall)

Outcome: 1-2% flagging rate with 95% accuracy
Pros:
  - Adapts to new patterns (learns from recent fraud)
  - Can detect subtle patterns (velocity spike, unusual merchant)
  - Better precision possible (fewer false positives)
Cons:
  - Less explainable ("model said so" vs. "matched rule X")
  - Requires labeled fraud data (need 1000+ confirmed frauds)
  - Operational overhead (monitoring, retraining, versioning)
```

**Recommendation: Hybrid Approach [2 marks]**
```
Best solution: Rules + ML

Stage 1: Use clear rules for obvious cases
├─ IF amount > $50K → Flag (high risk, rare)
├─ IF country change same day → Flag (clear pattern)
├─ IF velocity spike (5 transactions in 1 min) → Flag
└─ Cost: Flag 0.5% (50K transactions)

Stage 2: Use ML for subtle cases
├─ ML model on remaining 99.5% transactions
├─ Learn patterns from actual fraud labels
├─ Flag additional 1-2% (high risk per model)
└─ Cost: Maintenance + compute (~$10K/month)

Result:
├─ Flagging rate: 1.5-2% (down from 5%)
├─ Manual review workload: 150K-200K/day (vs. 500K)
├─ Accuracy: 90-95% true positives
└─ Explainability: Clear rules + ML scores
```

**Cost-Benefit Analysis [2 marks]**
```
Current state (all rules):
├─ Manual review: 500K/day × $1/review = $500K/day
├─ Cost/year: $182M
└─ False negatives (missed fraud): ~$50M/year

Proposed (Hybrid):
├─ Manual review: 150K/day × $1/review = $150K/day
├─ ML infrastructure: $10K/month = $120K/year
├─ Cost/year: $55M + $120K = $55.1M
├─ False negatives (better detection): ~$10M/year
└─ Total savings: $182M - $55M - $10M = $127M/year

ROI: Saves $127M/year with $500K upfront investment → Highly justified
```

## Q15. Handling Concept Drift in Churn Prediction [8 Marks]
[TYPE: Scenario-based, Production Issue]

A telecom company deployed a churn prediction model 6 months ago. It worked well initially (88% AUC). Recently:
- Accuracy dropped to 76% AUC
- Business metrics: Fewer customers successfully retained (fewer interventions are working)

Investigation reveals:
- Customer behavior changed (pandemic effects wearing off; return to office)
- New competitor entered market (changed competitive landscape)
- Product changes (new features launched; usage patterns shifted)

Question: Root cause analysis and remediation strategy [8 marks]

**ANSWER:**

**Root Cause Analysis [2 marks]**

```
Likely causes (ranked by probability):

1. CONCEPT DRIFT (80% likely)
   ├─ Definition: Underlying relationship between features and churn changed
   ├─ Why: Competitive landscape shift, customer priorities changed
   ├─ Evidence: Model accuracy degraded; feature importance may have shifted
   ├─ Example: "Job stability" less important; "competitor offers" more important
   └─ Impact: Model trained on old patterns; new data follows different rules

2. DATA DRIFT (15% likely)
   ├─ Definition: Input feature distributions changed
   ├─ Why: Pandemic effects normalizing; customer demographics/usage shifting
   ├─ Evidence: Check if feature distributions significantly different
   ├─ Example: Avg revenue per user shifted from $50 → $60
   └─ Impact: Model operates outside training distribution

3. LABEL DRIFT (5% likely)
   ├─ Definition: Definition of "churn" changed
   ├─ Why: Unlikely unless company policy changed
   ├─ Evidence: Check how churn is defined (30-day inactivity? cancellation?)
   └─ Impact: Training labels no longer match current churn behavior
```

**Diagnostic Steps [2 marks]**

```
Step 1: Feature Distribution Analysis
├─ Compare current vs. training data distributions
├─ For each feature: Calculate KL divergence or Wasserstein distance
├─ If >10% of features have significant drift → Data drift confirmed
└─ Action: Normalize features or retrain

Step 2: Feature Importance Comparison
├─ Retrain model on recent 3 months of data
├─ Compare feature importances between old and new model
├─ If top features changed → Concept drift likely
├─ Example: Old model: [Usage, Tenure, Price] 
           New model: [Competitor_Offers, Support_Tickets, Price]
└─ Action: Investigate why importance shifted

Step 3: Performance on Time Slices
├─ Evaluate old model on:
│  ├─ Training data (6 months ago): 88% AUC (baseline)
│  ├─ Data from 3-4 months ago: 85% AUC (slight degradation)
│  ├─ Recent data (last month): 76% AUC (major degradation)
│  └─ Pattern: Degradation increases with time → Drift confirmed
└─ Timeline: When did degradation start? (points to event that caused shift)

Step 4: Business Event Timeline
├─ Correlate model degradation with:
│  ├─ Competitor market entry date
│  ├─ Product launch date
│  ├─ Pandemic-related changes
│  ├─ Marketing campaign changes
│  └─ Pricing changes
└─ Match: If degradation started after event X → X likely cause

Step 5: Manual Review of Errors
├─ Collect recent false positives (predicted churn, didn't churn)
├─ Collect recent false negatives (predicted no churn, but churned)
├─ Interview customers in error buckets
├─ Question: "Why didn't you churn?" or "What made you churn?"
└─ Insight: Understand new churn drivers model missed
```

**Remediation Strategy [2 marks]**

```
Phase 1: Immediate Actions (Week 1)
├─ Pause automatic decision-making (prevent bad interventions)
├─ Manual review: Business team manually decide on interventions
├─ Cost: Higher manual effort, but prevents harm
├─ Monitoring: Track if manual interventions work better

Phase 2: Root Cause Investigation (Weeks 1-2)
├─ Run diagnostic steps above
├─ Determine: Concept drift vs. data drift vs. both
├─ Identify: Which features/drivers changed
├─ Timeline: When did change occur

Phase 3: Retraining (Week 2-3)
├─ Collect recent labeled data (customers from last 3 months)
├─ Include new features capturing:
│  ├─ Competitor offerings (web scrape competitor website)
│  ├─ Market conditions (unemployment rate, economic sentiment)
│  ├─ Customer interaction quality (support ticket sentiment)
│  └─ Product usage patterns (new feature adoption)
│
├─ Retrain model on recent data
├─ Expected improvement: 76% → 84-86% AUC
├─ Validation: Test on holdout recent data
└─ Threshold: Only deploy if AUC ≥ 85%

Phase 4: Deployment & Monitoring (Week 3-4)
├─ A/B test: New model vs. manual decisions (50-50 split)
├─ Measure: Retention rate, intervention success rate
├─ Duration: 2 weeks minimum
├─ Comparison: If new model ≥ manual decisions → Roll out 100%
│
├─ Enhanced monitoring setup:
│  ├─ Track prediction drift (distributions changing)
│  ├─ Track performance drift (accuracy declining)
│  ├─ Automatic retraining trigger: If AUC drops >10% from baseline
│  └─ Alert threshold: Notify team if drift detected
└─ Retraining cadence: Monthly (or when drift detected)
```

**Long-term Prevention [2 marks]**

```
Build drift-resilience into future models:

1. Online Learning / Continuous Updates
   ├─ Incrementally update model as new data arrives
   ├─ Instead of: Batch retraining every 6 months
   ├─ Use: Online algorithms (SGD, incremental PCA)
   └─ Benefit: Automatically adapt to gradual changes

2. Feature Monitoring Pipeline
   ├─ Track all feature distributions daily
   ├─ Alert if any feature drifts >5% from baseline
   ├─ Automatic investigation: Why did feature change?
   └─ Benefit: Catch data issues before model degrades

3. Ensemble & Diversity Approach
   ├─ Train multiple models on different data snapshots
   ├─ Combine predictions (reduce impact of individual model drift)
   ├─ Mix different algorithms (linear + tree-based)
   └─ Benefit: Robust to concept drift

4. Automatic Retraining Triggers
   ├─ Monitor: Prediction distribution, feature drift, accuracy
   ├─ Trigger: If any metric crosses threshold
   ├─ Action: Automatically retrain on recent data
   └─ Benefit: Faster response to changes

5. External Data Integration
   ├─ Include market data (competitor actions, economic indicators)
   ├─ Feature: "Competitor offers strong deals this week"
   ├─ Benefit: Model aware of external factors causing drift
   └─ Implementation: Real-time data feeds
```

## Q18. Feature Interaction Detection [7 Marks]

You have a CLV model with 50 features. Some features interact (not independent).

Question: How to detect and test feature interactions? [7 marks]

**ANSWER:**

**Method 1: Correlation Analysis [1.5 marks]**
```
Calculate pairwise correlations
├─ If Corr(Age, Income) > 0.9 → Strong interaction
├─ Likely redundant; keep only one
└─ Implementation: Pandas corr(), seaborn heatmap
```

**Method 2: Tree-based Feature Importance [1.5 marks]**
```
Train XGBoost / Random Forest
├─ Trees naturally capture interactions
├─ Feature importance shows combined importance
├─ Compare: Individual importance vs. combined
└─ If sum(importance_A + importance_B) << importance(A,B) → Interaction
```

**Method 3: Partial Dependence Plots [2 marks]**
```
Visualize: How output changes with feature X holding others constant
├─ If curves differ by value of Y → Interaction exists
├─ Example: "Impact of Age differs by Income level"
└─ Implementation: Scikit-learn PDP, Plotly
```

**Method 4: Permutation Feature Importance [1.5 marks]**
```
Shuffle one feature at a time
├─ Measure: Performance drop when feature shuffled
├─ If shuffling A affects impact of B → Interaction
└─ Benefit: Model-agnostic, works with any algorithm
```

## Q19. Handling Imbalanced Classes in Fraud Detection [7 Marks]

Fraud dataset: 99.9% legitimate transactions, 0.1% fraud

Training model naively achieves 99.9% accuracy by predicting everything as "not fraud"

Design solution: [7 marks]

**ANSWER:**

**Solution 1: Class Weighting [1.5 marks]**
```
Give more weight to minority class during training
├─ Weight_fraud = (Total_samples / 2×Fraud_samples)
├─ Weight_legitimate = (Total_samples / 2×Legitimate_samples)
├─ Effect: Model penalized more for missing frauds
└─ Benefit: Simple, works with any algorithm
```

**Solution 2: Resampling [1.5 marks]**
```
Option A: Oversample minority (duplicate fraud samples)
├─ Create synthetic fraud examples
├─ Dataset: 50-50 fraud vs legitimate
├─ Risk: Overfitting (duplicates create artificial patterns)

Option B: Undersample majority (remove some legitimate)
├─ Keep all fraud, random sample of legitimate
├─ Dataset: 50-50 (or 1-10 ratio)
├─ Risk: Throw away data
```

**Solution 3: SMOTE (Synthetic Minority Oversampling) [1.5 marks]**
```
Create synthetic frauds by interpolation
├─ For each real fraud: Find K nearest fraud neighbors
├─ Create synthetic fraud at random point between them
├─ Result: More diverse fraud examples (not duplicates)
└─ Benefit: Better generalization than simple oversampling
```

**Solution 4: Threshold Tuning [1.5 marks]**
```
Instead of threshold P(fraud) > 0.5, use P(fraud) > 0.1
├─ More sensitive: Catch more frauds (higher recall)
├─ Trade-off: More false positives (lower precision)
├─ Decision: Choose threshold by cost analysis
│  - Cost of false negative (missed fraud): $1000
│  - Cost of false positive (false alert): $5
│  - Choose threshold that minimizes total cost
```

**Solution 5: Ensemble Approach [1 mark]**
```
Combine multiple strategies:
├─ SMOTE + class weights + threshold tuning
├─ Multiple models with different hyperparameters
├─ Vote: Flag as fraud only if majority agree
└─ Benefit: Robust to individual model biases
```

**Recommendation: Use all 5 together [1 mark]**
```
Pipeline:
├─ Oversample minority using SMOTE (double fraud examples)
├─ Apply class weights (10:1 fraud:legitimate)
├─ Threshold: P(fraud) > 0.15 (not 0.5)
├─ Expected: 95% recall (catch 95% of fraud) + 90% precision
└─ Validate on holdout set before production
```

## Q20. Real-time Feature Computation Architecture [8 Marks]

Ride-sharing app needs features computed in <100ms for driver ranking.

Features needed:
- Driver acceptance rate (historical: how often accepts?)
- Driver location (real-time: GPS)
- Driver ETA (real-time: navigation API)

Design: How to compute these fast? [8 marks]

**ANSWER:**

**Feature 1: Driver Acceptance Rate (Pre-computed) [2 marks]**

```
Pipeline:
├─ Batch job (hourly): Compute acceptance rate for all drivers
│  └─ SQL: SELECT driver_id, COUNT(accepted) / COUNT(requests) FROM requests_last_7_days
├─ Store in Redis (in-memory cache)
│  └─ Key: "driver_acceptance:{driver_id}" → Value: 0.85
├─ Serving: Lookup from Redis in <5ms
└─ Tradeoff: 1-hour staleness OK for acceptance rate
```

**Feature 2: Driver Location (Real-time Stream) [2 marks]**

```
Pipeline:
├─ GPS updates stream (Kafka/Pub-Sub)
│  └─ Driver app sends location every 10 seconds
├─ Stream processor (Spark/Kafka Streams)
│  ├─ Receives: GPS coordinates
│  ├─ Computes: Distance to passenger
│  └─ Updates cache immediately
├─ Store in Redis hash
│  └─ Key: "driver_location:{driver_id}" → Value: {lat, lon}
├─ Serving: Lookup in <5ms
└─ Freshness: <30 seconds stale
```

**Feature 3: Driver ETA (On-demand) [2 marks]**

```
Pipeline:
├─ Ride request arrives
├─ Query external API (Google Maps / Mapbox)
│  ├─ Input: Driver current location, Passenger location
│  ├─ Output: ETA in seconds
│  └─ Latency: 50-100ms
├─ Cache result for 30 seconds (avoid redundant API calls)
├─ Serving: Return from cache if available; else call API
└─ Tradeoff: Slight staleness acceptable; API calls expensive
```

**Architecture Diagram [1 mark]**

```
Request arrives: Get driver ETA

[Ride Request API] 
  ↓ (Must respond in <100ms)
  ├─→ Cache lookup (acceptance rate): <5ms ✓
  ├─→ Cache lookup (location): <5ms ✓
  ├─→ Cache lookup (ETA from 30s ago): <1ms ✓
  │   If not cached → Call Maps API: ~50ms
  ├─ Combine features
  └─→ ML Model scores: <20ms
  └─ Return top 3 drivers to send push notifications

Total latency: 25-75ms (well within 100ms)
```

**Failure Handling [1 mark]**

```
If cache down: Use stale data from previous request
├─ Degradation acceptable (1-5 min stale data)

If API down: Use cached ETA or estimate (distance/speed)
├─ Reasonable fallback, not perfect

If model slow: Revert to heuristic (sort by rating + distance)
├─ Always have fast fallback
```
