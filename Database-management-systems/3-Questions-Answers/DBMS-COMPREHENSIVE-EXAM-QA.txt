Q1. UNIVERSITY DATABASE DESIGN & NORMALIZATION | 8 marks
================================================================================

SCENARIO:
A university stores student information: StudentID, Name, Address, Phone, 
DepartmentID, DepartmentName, CourseID, CourseName, Grade, Semester.

Currently one table with repeating course information. Poor query performance. 
Data anomalies when departments change name.

PROBLEMS:
- Insert anomaly: Can't add new department without student
- Update anomaly: Changing "CS Department" name requires updating 10K rows
- Delete anomaly: Removing last student deletes department info
- Redundant storage: "CS Department" repeated 5000 times

---

(a) IDENTIFY ALL ANOMALIES. HOW DO THEY AFFECT OPERATIONS? (2 marks)

ANSWER:

**Anomaly Type 1: INSERT ANOMALY**

Problem:
- New department "Electronics" hired but no students yet
- Can't insert row: StudentID is PRIMARY KEY (can't be NULL)
- Result: Electronics department not in database until first student enrolls

Impact:
- Administrative inefficiency: Can't plan courses for new department
- Data model doesn't reflect reality: Department exists but not recorded
- Business impact: Hiring delay, payroll issues

Example:
Insert into Student values (NULL, 'Dr. Kumar', '...', 'Elect', 'Electronics', NULL, NULL, NULL, NULL)
ERROR: PRIMARY KEY violation (StudentID can't be NULL)

---

**Anomaly Type 2: UPDATE ANOMALY**

Problem:
- "Computer Science Department" renamed to "CS & AI Department"
- Must update 5000 student records where DepartmentName = 'CS Department'
- If update incomplete: Inconsistent data (some old name, some new)
- If error mid-update: Partial change corrupts database

Data example (10,000 rows total, 5000 for CS dept):
Update Student set DepartmentName = 'CS & AI Department' where DepartmentID = 'CS'
5000 rows updated...error occurs after 3000 rows...
Result: 3000 rows updated, 2000 rows still have old name
       Database in INCONSISTENT state

Impact:
- Data inconsistency: "Which name is correct?"
- Query unpredictability: 'CS Department' gives 2000 rows, 'CS & AI Department' gives 3000
- Report accuracy: Total dept count wrong
- Maintenance nightmare: Developers don't trust data

---

**Anomaly Type 3: DELETE ANOMALY**

Problem:
- Last student in "Mechanical Engineering" dept graduates
- Delete student row (necessary for cleanup)
- Side effect: Mechanical Engineering department info deleted too!
- Can't distinguish between "No students" vs "Department doesn't exist"

Data example:
Before: Student(1001, 'Raj', ..., 'ME', 'Mechanical Engineering', ...)
        (This is the ONLY row with ME department)

Delete from Student where StudentID = 1001
Result: 1) Student Raj removed ✓
        2) Mechanical Engineering department information LOST ✗

After: No way to know ME department ever existed

Impact:
- Accidental data loss: Department metadata destroyed
- Historical records incomplete: Can't do "departments over time" analysis
- Compliance issue: Audit trail shows dept never existed (legally problematic)

---

**SUMMARY TABLE: Anomaly Effects**

| Anomaly | Operation Blocked | Data Lost | Inconsistency Risk | Maintenance Cost |
|---------|-------------------|-----------|-------------------|-----------------|
| INSERT  | Add new data      | No        | No                 | Low             |
| UPDATE  | Edit existing     | No        | HIGH (partial)     | VERY HIGH       |
| DELETE  | Remove data       | YES       | No                 | Medium          |

(b) DESIGN ER MODEL WITH PROPER ENTITIES AND RELATIONSHIPS (2 marks)

ANSWER:

ER Model Design (Proper Normalization):

```
┌─────────────────────────────────────────────────────────────────┐
│                        STUDENTS                                  │
├─────────────────────────────────────────────────────────────────┤
│ PK: StudentID                                                   │
│ ForeignKey: DepartmentID (FK to Department)                     │
│ Attributes: Name, Address, Phone                                │
└─────────────────────────────────────────────────────────────────┘
              │
              │ Enrolls (1:M relationship)
              │
         ┌────▼─────────────────────────────────────────────────┐
         │              ENROLLMENT                              │
         ├────────────────────────────────────────────────────┤
         │ PK: (StudentID, CourseID, Semester)                │
         │ FK: StudentID → Students                           │
         │ FK: CourseID → Course                              │
         │ Attributes: Grade                                  │
         └────────────────────────────────────────────────────┘
                                │
                                │ Takes (M:N relationship)
                                │
                        ┌───────▼────────────────────┐
                        │       COURSE               │
                        ├────────────────────────────┤
                        │ PK: CourseID               │
                        │ FK: DepartmentID (FK)      │
                        │ Attributes: CourseName     │
                        └───────┬────────────────────┘
                                │
                                │ Offers (M:1)
                                │
                ┌───────────────▼──────────────────────┐
                │       DEPARTMENT                      │
                ├───────────────────────────────────────┤
                │ PK: DepartmentID                     │
                │ Attributes: DepartmentName           │
                └───────────────────────────────────────┘
```

Key Design Principles Applied:

1. **Separate Department entity**: DepartmentName not repeating in Student
   - Change dept name → Update 1 row in Department
   - Not 5000 rows in Student

2. **Eliminate repeating groups**: CourseID & CourseName separate
   - Course is own entity with DepartmentID
   - Prevents repeating course info per student

3. **Junction table (Enrollment)**: Breaks M:N relationship
   - Student : Course = M:N (one student, many courses; one course, many students)
   - Create Enrollment table: (StudentID, CourseID, Semester, Grade)
   - Now: Student → Enrollment → Course (1:M:1 chain)

```
1002      | M101     | Thermody   | A     | Fall2024
```

✓ 1NF achieved: All attributes atomic, no repeating groups

**STEP 2: CONVERT TO 2NF (Remove Partial Dependencies)**

Rule: Non-key attributes must depend on ENTIRE primary key (not partial)

Analysis of StudentInfo:
```
PK: StudentID (single column)
├─ Name depends on StudentID ✓ (fully dependent)
├─ Address depends on StudentID ✓ (fully dependent)  
├─ DepartmentID depends on StudentID ✓ (fully dependent)

```

```
Table 1: Student

StudentID | Name  | Address | DepartmentID
1001      | Raj   | 123 St  | CS
1002      | Priya | 456 Ave | ME

(All non-keys fully depend on StudentID)

Table 2: Department (Remove partial dependency)
PK: DepartmentID
DepartmentID | DepartmentName
CS           | Comp Science
ME           | Mech Eng

(DepartmentName fully depends on DepartmentID)
```

Analysis of StudentCourses:
```
PK: (StudentID, CourseID) - Composite key
├─ Grade depends on (StudentID, CourseID) ✓ (need both to identify grade)
├─ Semester depends on (StudentID, CourseID) ✓ (when student takes course)
└─ CourseName depends on CourseID ✗ (only need CourseID, not StudentID)

Partial Dependency found: CourseName depends only on CourseID
```

Decompose StudentCourses:


---

**STEP 3: CONVERT TO 3NF (Remove Transitive Dependencies)**

Rule: Non-key attributes must depend directly on PK (not transitively through other non-keys)

Check all 2NF tables:

```
Table: Student

StudentID → Name (direct) ✓
StudentID → Address (direct) ✓
StudentID → DepartmentID (direct) ✓

No transitive dependencies found ✓

Table: Department
PK: DepartmentID

No transitive dependencies ✓

Table: Enrollment
PK: (StudentID, CourseID)
(StudentID, CourseID) → Grade (direct) ✓
(StudentID, CourseID) → Semester (direct) ✓

No transitive dependencies ✓

Table: Course
PK: CourseID
CourseID → CourseName (direct) ✓

No transitive dependencies ✓
```

✓ 3NF achieved: No non-key attribute depends on another non-key attribute

---

**STEP 4: CONVERT TO BCNF (Remove all anomalies)**

Rule: Every determinant must be a candidate key

BCNF check: For every functional dependency X → Y, X must be a candidate key

```
Current BCNF-compliant tables:

1. Student
   PK: StudentID
   Determinants: StudentID only
   StudentID is candidate key ✓

2. Department  
   PK: DepartmentID
   Determinants: DepartmentID only
   DepartmentID is candidate key ✓

3. Enrollment
   PK: (StudentID, CourseID)
   Determinants: (StudentID, CourseID) only
   Composite key is candidate key ✓

4. Course
   PK: CourseID
   Determinants: CourseID only
   CourseID is candidate key ✓
```

✓ BCNF achieved: All determinants are candidate keys

```
Department
├─ PK: DepartmentID
├─ Attributes: DepartmentName
└─ Rows: (CS, Comp Science), (ME, Mech Eng)

├─ PK: StudentID
```

(d) WRITE SQL CREATE TABLE STATEMENTS FOR FINAL SCHEMA (2 marks)

ANSWER:

```sql
-- Department table (independent)
CREATE TABLE Department (
    DepartmentID VARCHAR(10) PRIMARY KEY,
    DepartmentName VARCHAR(100) NOT NULL UNIQUE,
    CreatedDate TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_name (DepartmentName)
);

-- Student table (depends on Department)
CREATE TABLE Student (
    StudentID INT PRIMARY KEY AUTO_INCREMENT,
    Name VARCHAR(100) NOT NULL,
    Address VARCHAR(255),
    Phone VARCHAR(15),
    DepartmentID VARCHAR(10) NOT NULL,
    EnrollmentDate DATE DEFAULT CURDATE(),
    FOREIGN KEY (DepartmentID) REFERENCES Department(DepartmentID),
    INDEX idx_dept (DepartmentID),
    INDEX idx_name (Name)
);

-- Course table (depends on Department)
CREATE TABLE Course (
    CourseID VARCHAR(10) PRIMARY KEY,
    CourseName VARCHAR(100) NOT NULL UNIQUE,
    DepartmentID VARCHAR(10) NOT NULL,
    Credits INT DEFAULT 3,
    Description TEXT,
    FOREIGN KEY (DepartmentID) REFERENCES Department(DepartmentID),
    INDEX idx_dept (DepartmentID),
    INDEX idx_name (CourseName)
);

-- Enrollment table (junction table, depends on Student & Course)
CREATE TABLE Enrollment (
    EnrollmentID INT PRIMARY KEY AUTO_INCREMENT,
    StudentID INT NOT NULL,
    CourseID VARCHAR(10) NOT NULL,
    Semester VARCHAR(20) NOT NULL,
    Grade VARCHAR(2),
    EnrollmentDate DATE DEFAULT CURDATE(),
    FOREIGN KEY (StudentID) REFERENCES Student(StudentID) ON DELETE CASCADE,
    FOREIGN KEY (CourseID) REFERENCES Course(CourseID) ON DELETE RESTRICT,
    UNIQUE KEY unique_enrollment (StudentID, CourseID, Semester),
    INDEX idx_student (StudentID),
    INDEX idx_course (CourseID),
    INDEX idx_semester (Semester)
);

-- View: Student-Course information (optional, for convenience)
CREATE VIEW StudentCourseView AS
SELECT 
    s.StudentID,
    s.Name,
    d.DepartmentName,
    c.CourseName,
    e.Grade,
    e.Semester
FROM Student s
JOIN Department d ON s.DepartmentID = d.DepartmentID
JOIN Enrollment e ON s.StudentID = e.StudentID
JOIN Course c ON e.CourseID = c.CourseID
ORDER BY s.StudentID, e.Semester, c.CourseName;
```

**Key Design Features:**

1. **Data Types**: Chosen for efficiency
   - VARCHAR for IDs (DepartmentID, CourseID vary in length)
   - INT for student count (can accommodate millions)
   - DATE for temporal data

2. **Constraints**:
   - PRIMARY KEY: Unique identification
   - FOREIGN KEY: Referential integrity (prevents orphan records)
   - UNIQUE: DepartmentName, CourseName (no duplicates)
   - NOT NULL: Essential fields always populated

3. **Indexes**:
   - On FK columns (DepartmentID, StudentID, CourseID): Faster joins
   - On Name columns: Faster search/filtering by name
   - On Semester: Faster queries by academic term

4. **Cascade/Restrict**:
   - ON DELETE CASCADE for Enrollment: If student deleted, their enrollments removed
   - ON DELETE RESTRICT for Course: Can't delete course if students enrolled

5. **View**: Optional convenience layer
   - Combines normalized tables back into single view
   - Applications can query view without knowing normalization structure

Q2. TRANSACTION ACID PROPERTIES UNDER FAILURE | 8 marks
================================================================================

SCENARIO:
Bank transfer: Account A (balance $1000) → Account B (balance $500).
Transfer $200. Process:
1. Read A balance: $1000
2. Deduct from A: $800
3. **System CRASHES here**
4. Add to B: $700
5. Write A: $800, Write B: $700

AFTER CRASH:
- Account A: $800 (money disappeared!)
- Account B: $500 (didn't receive)
- Total money lost: $200

---

(a) WHICH ACID PROPERTY VIOLATED? EXPLAIN IMPACT (2 marks)

ANSWER:

**Primary Violation: ATOMICITY**

Atomicity Definition: "Either the entire transaction succeeds (commits) or it fails entirely (aborts). No partial updates."

What happened:
- Transaction partially executed: Steps 1-3 completed
- Steps 4-5 not executed: System crashed
- Result: Database in inconsistent state (Step 2 persisted, Steps 4-5 didn't)

Impact:
✗ Account A: Deducted $200 (persisted before crash)
✗ Account B: Not credited (never executed after crash)
✗ Total money: $1200 → $1300 (money duplicated, not transferred)

Business Impact:
- Bank liability: Account holder sees $800, but bank transferred to wrong place
- Trust loss: Customer complaints
- Audit failure: Money missing/duplicated
- Regulatory violation: Financial records don't match physical reality

---

**Secondary Violation: DURABILITY**

Durability Definition: "Once transaction commits, changes must survive any failure (crashes, power loss, disk failure)."

The problem:
- Steps 1-3 were executed (not explicitly committed)
- System crashed before COMMIT statement
- Changes should NOT be durable (should rollback)
- But they persisted anyway

Impact:
- Assumption violated: "What's written is safe"
- Database corrupted on restart
- Recovery mechanism failed

---

**Tertiary Violation: CONSISTENCY**

Consistency Definition: "Database moves from valid state to valid state. All integrity constraints respected."

Before transaction: Total money = $1000 + $500 = $1500 ✓ (consistent)
After crash: Total money = $800 + $500 = $1300 ✗ (inconsistent, money created!)

Impact:
- Database invariant violated: Total money != sum of accounts
- Financial integrity broken
- Reports show wrong totals

---

(b) HOW WOULD PROPER TRANSACTION HANDLING PREVENT THIS? (2 marks)

ANSWER:

**Key Mechanism: Write-Ahead Logging (WAL)**

Principle: Before modifying database, write intention to log file (on disk)

Process:

```
Step 1: BEGIN TRANSACTION
  ├─ Write to LOG: "Transaction START"
  └─ Assign TransactionID = T1

Step 2: UPDATE Account A SET balance = 800
  ├─ Write to LOG: "T1: UPDATE AccountA, oldValue=1000, newValue=800"
  ├─ Write lock acquired on Account A
  └─ Execute update in memory buffer

Step 3: UPDATE Account B SET balance = 700
  ├─ Write to LOG: "T1: UPDATE AccountB, oldValue=500, newValue=700"
  ├─ Write lock acquired on Account B
  └─ Execute update in memory buffer

Step 4: COMMIT TRANSACTION
  ├─ Write to LOG: "T1: COMMIT" ← CRITICAL: Write to disk FIRST
  ├─ Wait for disk confirmation (fsync)
  ├─ Now safe to write buffers to database
  └─ Release all locks
  └─ Acknowledge to application: "Transaction committed"

Step 5: Write buffers to actual database
```

If crash occurs BEFORE Step 4 (before COMMIT in log):
- LOG shows incomplete transaction
- On restart: Recovery process reads LOG
- Finds no COMMIT record for T1
- Uses UNDO logs to rollback changes
- Database restored to consistent state (before transfer attempt)

If crash occurs AFTER Step 4 (COMMIT in log):
- LOG shows completed transaction
- On restart: Recovery process reads LOG
- Finds COMMIT record for T1
- Uses REDO logs to reapply changes
- Database restored to consistent state (after transfer)

Result: Either transfer complete or transfer didn't happen (atomicity guaranteed)

---

(c) IMPLEMENT USING BEGIN/COMMIT/ROLLBACK. SHOW CODE (2 marks)

ANSWER:

**SQL Implementation:**

```sql
-- Proper transaction handling

BEGIN TRANSACTION;  -- Start transaction (implicit or explicit)

-- Set transaction properties for safety
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
SET AUTOCOMMIT OFF;

-- Step 1: Deduct from Account A
UPDATE Account 
SET balance = balance - 200,
    last_modified = NOW()
WHERE account_id = 'A' AND balance >= 200;  -- Check constraint

IF @@ROWCOUNT = 0 THEN
    -- Insufficient funds
    ROLLBACK;  -- Abort entire transaction
    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Insufficient funds';
END IF;

-- Step 2: Add to Account B
UPDATE Account 
SET balance = balance + 200,
    last_modified = NOW()
WHERE account_id = 'B';

IF @@ROWCOUNT = 0 THEN
    -- Account B doesn't exist
    ROLLBACK;  -- Abort entire transaction
    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Account B not found';
END IF;

-- Step 3: Record transaction in audit log
INSERT INTO Transaction_Log (from_account, to_account, amount, status, created_at)
VALUES ('A', 'B', 200, 'PENDING', NOW());

-- If we reach here: All operations succeeded
COMMIT;  -- Make changes permanent and durable

-- After COMMIT:
-- - Both UPDATE statements are persisted
-- - Audit log recorded
-- - All locks released
-- - Transaction complete

SELECT balance FROM Account WHERE account_id IN ('A', 'B');
-- Output: A=800, B=700
```

**Error Handling Version:**

```sql
DELIMITER $$

CREATE PROCEDURE TransferMoney(
    IN p_from_account VARCHAR(10),
    IN p_to_account VARCHAR(10),
    IN p_amount DECIMAL(10,2),
    OUT p_status VARCHAR(50)
)
BEGIN
    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        ROLLBACK;
        SET p_status = 'TRANSFER_FAILED';
    END;
    
    START TRANSACTION;
    
    -- Deduct from source
    UPDATE Account 
    SET balance = balance - p_amount
    WHERE account_id = p_from_account 
      AND balance >= p_amount;
    
    IF ROW_COUNT() = 0 THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Invalid source or insufficient balance';
    END IF;
    
    -- Add to destination
    UPDATE Account 
    SET balance = balance + p_amount
    WHERE account_id = p_to_account;
    
    IF ROW_COUNT() = 0 THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Invalid destination';
    END IF;
    
    -- Log transaction
    INSERT INTO Transaction_Log 
    VALUES (NULL, p_from_account, p_to_account, p_amount, 'COMPLETE', NOW());
    
    COMMIT;
    SET p_status = 'TRANSFER_SUCCESS';
END $$

DELIMITER ;

-- Usage:
CALL TransferMoney('A', 'B', 200, @status);
SELECT @status;
```

(d) WHAT IF SECONDARY CRASHES DURING COMMIT? DESIGN RECOVERY MECHANISM (2 marks)

ANSWER:

**Scenario: Crash During Commit Phase**

```
Timeline:
T1: Coordinator writes "COMMIT" to log (disk) ✓
T2: Coordinator sends COMMIT to Participant 1 ✓
T3: Participant 1 receives COMMIT, starts writing...
T4: **CRASH** (Participant 1 crashes mid-write)
T5: Participant 1 reboots after power failure

Question: How much was written? Data inconsistent?
```

---

**Recovery Mechanism Using Transaction Log:**

**On crash recovery:**

```
Phase 1: READ TRANSACTION LOG
├─ Open transaction log on reboot
├─ Scan log entries chronologically
│
Entry 1: "T1 START" (T1 started)
Entry 2: "T1 UPDATE Account A: 1000→800"
Entry 3: "T1 UPDATE Account B: 500→700"
Entry 4: "T1 COMMIT" (Commit decision made)
Entry 5: **END OF LOG** (crash happened during write)
│
├─ Status: T1 has COMMIT marker → Transaction should be committed
└─ Action: REDO T1 (reapply all changes)

Phase 2: REDO RECOVERY
├─ Read all committed transactions (have COMMIT marker)
├─ For each committed but not fully persisted:
│  ├─ Account A: Set balance = 800 (from REDO log)
│  ├─ Account B: Set balance = 700 (from REDO log)
│  └─ Verify both updates complete
└─ Result: Transaction T1 fully persisted

Phase 3: VERIFY CONSISTENCY
├─ Total money: 800 + 700 = 1500 ✓ (consistent, matches pre-transaction)
└─ Database integrity maintained
```

**Write-Ahead Log Structure:**

```
Transaction Log file format:
┌─────────────────────────────────────────┐
│ LSN  | TransID | Type    | Data         │
├─────────────────────────────────────────┤
│ 100  | T1      | START   | -            │ ← Before writing any data
│ 101  | T1      | WRITE   | Acct A: 800  │ ← Before modifying A
│ 102  | T1      | WRITE   | Acct B: 700  │ ← Before modifying B
│ 103  | T1      | COMMIT  | -            │ ← Before releasing locks
│ 104  | T1      | END     | -            │ ← After persisted to storage
└─────────────────────────────────────────┘

If crash at LSN 103.5 (during COMMIT write):
├─ Log contains: START, WRITE A, WRITE B, partial COMMIT
├─ Recovery detects incomplete COMMIT marker
├─ Checks undo/redo logs: COMMIT was intended
├─ Redoes all changes
└─ Database recovers to committed state
```

**Two-Phase Commit Recovery:**

```
Distributed scenario (Coordinator + 2 Participants):

Phase 1 (Prepare): All vote YES → Coordinator decides COMMIT
Phase 2 (Commit): 
  - Participant 1: Commits ✓
  - Participant 2: **CRASHES** mid-commit
  - Coordinator: Sent COMMIT, waiting for acks

On Participant 2 restart:
├─ Read local transaction log
├─ Find: "T1 COMMIT marker" (decided by coordinator)
├─ Action: REDO all changes to match committed state
├─ Contact Coordinator: "T1 recovery complete"
├─ All participants now consistent
└─ Transaction fully propagated

Guarantee: Either all commit or all abort (atomicity maintained)
```
