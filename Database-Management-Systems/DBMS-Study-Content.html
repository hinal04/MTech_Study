1.1 Introduction to Data Management Systems

A Data Management System is software that captures, stores, organises, and retrieves data so that users and applications can work with it efficiently and reliably.

Why formal data management matters

ConcernExplanation
Data sharingMultiple users and applications need concurrent access to the same data.
IntegrityRules (constraints) must keep data correct at all times.
EfficiencyAs data grows, brute-force searching becomes impractical — indexed structures are essential.
SecurityOnly authorised users should read or modify specific data.
RecoveryAfter a crash, data must be restored to a consistent state.

1.2 Evolution: File Systems → DBMS

1.2.1 The File System Era

In early computing every application managed its own flat files. This caused well-known problems:

ProblemWhat goes wrong
Data redundancySame data (e.g. customer name) stored in many files across different programs.
InconsistencyOne copy updated, others not — conflicting versions.
Difficulty in accessEvery new query may require writing a new program.
Data isolationData scattered across files in different formats.
Integrity problemsNo central mechanism to enforce constraints like "balance ≥ 0".
Atomicity problemsA crash midway through a multi-step update leaves data in a partial state.
Concurrent-access anomaliesTwo users updating the same file simultaneously can corrupt data.
Security issuesFile-level permissions are too coarse for field-level control.

1.2.2 The DBMS Solution

A Database Management System (DBMS) provides:

  1. Data definition — DDL to specify schema, types, constraints.
  2. Data manipulation — DML to insert, update, delete, and query.
  3. Controlled access — Concurrency control, backup/recovery, authorisation, integrity enforcement.

Key advantages over file systems:

  • Program–data independence: Schema stored in a catalog; storage changes don't force application rewrites.
  • Data abstraction: Users see logical views, not physical storage details.
  • Multiple views: Different users see different subsets of the same data.
  • Reduced redundancy: Centralised storage + normalisation.
  • Transaction support: ACID properties guarantee reliable processing.

1.2.3 The Three-Schema Architecture (ANSI/SPARC)

┌─────────────────────────────────┐ │ External Level (User Views) │ ← View 1, View 2 … ├─────────────────────────────────┤ │ Conceptual Level (Logical) │ ← Entities, relationships, constraints ├─────────────────────────────────┤ │ Internal Level (Physical) │ ← Files, indexes, blocks on disk └─────────────────────────────────┘
  • Logical data independence — Change the conceptual schema without affecting external views.
  • Physical data independence — Change internal storage without affecting the conceptual schema.

1.3.2 Schema vs. Instance

  • Schema (intension): Structure/description of the database — changes rarely.
  • Instance (extension): The actual data at a point in time — changes with every insert/update/delete.
Analogy: Schema = table headers + data types. Instance = the rows currently in the table.

1.4 Relational Database Fundamentals

1.4.1 The Relational Model (Codd, 1970)

TermMeaning
RelationA table with rows and columns.
TupleA single row.
AttributeA named column.
DomainSet of allowed values for an attribute.
DegreeNumber of attributes.
CardinalityNumber of tuples.
Relation schemaRelation name + attribute list, e.g. STUDENT(ID, Name, Age).

1.4.2 Properties of Relations

  1. Each tuple is distinct (no duplicate rows).
  2. Tuple ordering is insignificant.
  3. Attribute ordering is insignificant (identified by name).
  4. Every attribute value is atomic (indivisible) — First Normal Form (1NF).

1.4.3 Keys

Key TypeDefinition
SuperkeyAny set of attributes that uniquely identifies a tuple.
Candidate keyA minimal superkey (removing any attribute breaks uniqueness).
Primary key (PK)The candidate key chosen by the designer.
Foreign key (FK)Attribute(s) referencing the PK of another relation.
Alternate keyA candidate key not chosen as PK.

1.4.4 Integrity Constraints

  • Entity integrity: No PK attribute can be NULL.
  • Referential integrity: FK value must be NULL or match an existing PK.
  • Domain constraints: Every value must belong to its attribute's defined domain.
  • Key constraints: No two tuples share the same PK value.

1.4.5 Relational Algebra (Overview)

OperationSymbolDescription

Union∪Combine tuples from two union-compatible relations.
Intersection∩Tuples common to both.
Difference−Tuples in one but not the other.
Cartesian product×Every tuple of A combined with every tuple of B.
Join⋈Combine related tuples on a condition.

1.5 Data Modelling: Entities, Attributes, Relationships

1.5.1 The ER Model (Chen, 1976)

  • Entities — Distinguishable real-world objects.
  • Attributes — Properties of entities.
  • Relationships — Associations among entities.

1.5.2 Entity Types

  • Strong entity: Has its own key attribute (e.g. EMPLOYEE with Emp_ID).
  • Weak entity: No key of its own; depends on an identifying (owner) entity via an identifying relationship. Uses a partial key + owner's PK.

1.5.3 Attribute Types

TypeDescriptionExample
SimpleAtomic, indivisibleFirstName
CompositeDivisible into sub-partsFullName → {First, Middle, Last}
Single-valuedOne value per entityDateOfBirth
Multi-valuedMultiple values per entityPhoneNumbers
DerivedComputed from other attributesAge (from DOB)
KeyUniquely identifies entityEmployeeID

1.5.4 Relationships

Degree: Unary (recursive), Binary (most common), Ternary.

Cardinality RatioMeaningExample
1:1Each side relates to at most one on the other.EMPLOYEE manages DEPARTMENT
1:NOne on "1" side relates to many on "N" side.DEPARTMENT has many EMPLOYEEs
M:NMany-to-many.STUDENT enrols in COURSEs

Participation: Total (mandatory, double line) — every entity must participate. Partial (optional, single line) — some may not.

1.5.5 ER-to-Relational Mapping Rules

ER ConstructRelational Mapping

Weak entityTable with partial key + owner's PK as FK; composite PK.

1:N relationshipAdd PK of "1" side as FK in the "N" side table.
M:N relationshipNew junction table; PKs of both as FKs; composite PK.
Multi-valued attributeSeparate table: value + FK to owner's PK.

1.6 Normalisation — Eliminating Redundancy

1.6.1 Functional Dependencies (FDs)

A functional dependency X → Y means: if two tuples have the same value for X, they must have the same value for Y.

TypeDefinitionExample
Full FDY depends on X, not on any proper subset of X.{Student_ID, Course_ID} → Grade
Partial FDY depends on a proper subset of a composite key.{Student_ID, Course_ID} → Student_Name (depends only on Student_ID)
Transitive FDX → Y → Z (Y is not a candidate key).Emp_ID → Dept_ID → Dept_Name

1.6.2 First Normal Form (1NF)

Rule: Every attribute value must be atomic. No repeating groups or multi-valued cells.

Violation: STUDENT(ID, Name, PhoneNumbers) where PhoneNumbers = {9876543210, 9123456789}. Fix: Create a separate STUDENT_PHONE table.

1.6.3 Second Normal Form (2NF)

Rule: 1NF + no partial dependencies (every non-key attribute depends on the entire composite PK).

Violation: ENROLMENT(Student_ID, Course_ID, Student_Name, Grade) — Student_Name depends only on Student_ID. Fix: Split into STUDENT(Student_ID, Student_Name) and ENROLMENT(Student_ID, Course_ID, Grade).

1.6.4 Third Normal Form (3NF)

Rule: 2NF + no transitive dependencies (no non-key attribute depends on another non-key).

Violation: EMPLOYEE(Emp_ID, Dept_ID, Dept_Name) — Dept_Name depends on Dept_ID, not directly on Emp_ID. Fix: Split into EMPLOYEE(Emp_ID, Dept_ID) and DEPARTMENT(Dept_ID, Dept_Name).

1.6.5 Boyce-Codd Normal Form (BCNF)

Rule: For every non-trivial FD X → Y, X must be a superkey. Stricter than 3NF.

1.6.6 Normalisation Summary

Normal FormRequirementEliminates
1NFAtomic values onlyRepeating groups, multi-valued cells
2NF1NF + no partial dependenciesPartial dependencies on composite PK
3NF2NF + no transitive dependenciesTransitive dependencies among non-key attrs
BCNFEvery determinant is a superkeyAll remaining FD anomalies

1.8 Indexing & File Structures

Why Indexes Matter

Without an index, finding a row requires a full table scan. An index maps column values to row locations — like a book's index.

Types of Indexes

Index TypeHow it worksBest for
B+ TreeSelf-balancing tree; leaf nodes linked for range scans. O(log n).Equality, range, prefix queries. Used by all major RDBMSs.
HashHash function maps keys to buckets. O(1) average.Equality lookups only. Cannot sort or range scan.
BitmapBit vector per distinct value. Bit i = 1 if row i has that value.Low-cardinality columns (Gender, Status). Data warehousing.

Clustered vs. Non-Clustered

AspectClusteredNon-Clustered (Secondary)
Physical orderRows stored in index order.Separate structure pointing to row locations.
Number per tableOnly one.Many can exist.
SpeedFastest for range scans on indexed column.Requires extra lookup (unless covering).
Covering index: Includes all columns needed by a query. The DBMS answers the query entirely from the index without touching the main table (index-only scan).

File Organisation Methods

MethodDescriptionBest for
Heap fileRows in no particular order.Bulk inserts; full table scans.
Sorted fileRows in order of a sort key.Range queries on the sort key.
Hash fileHash function determines bucket.Equality lookups.
B+ tree fileRows in leaf nodes of a B+ tree.General purpose.

1.9 Views in SQL

A view is a virtual table defined by a SELECT query. It does not store data — the underlying query executes each time.

CREATE VIEW High_Earners AS
SELECT Emp_ID, First_Name, Last_Name, Salary
FROM EMPLOYEE
WHERE Salary > 100000;

Benefits: Simplification, security (expose only certain columns/rows), logical data independence, consistent business definitions.

Materialised view: Physically stores the result. Must be refreshed when data changes. Faster reads, risk of stale data.

1.10 Stored Procedures, Functions, and Triggers

Stored Procedures

CREATE PROCEDURE GiveRaise(IN dept INT, IN pct DECIMAL)
BEGIN
    UPDATE EMPLOYEE
    SET Salary = Salary * (1 + pct / 100)
    WHERE Dept_ID = dept;
END;

-- Call it
CALL GiveRaise(5, 10);

Triggers

A trigger automatically fires on INSERT, UPDATE, or DELETE events. Timing: BEFORE, AFTER, or INSTEAD OF.

CREATE TRIGGER salary_audit
AFTER UPDATE OF Salary ON EMPLOYEE
FOR EACH ROW
BEGIN
    INSERT INTO SALARY_AUDIT_LOG (Emp_ID, Old_Salary, New_Salary, Change_Date)
    VALUES (OLD.Emp_ID, OLD.Salary, NEW.Salary, CURRENT_TIMESTAMP);
END;
Caution: Overuse of triggers makes debugging difficult — they execute implicitly and can chain.

2.1 SQL Overview

SQL (Structured Query Language) is the standard language for relational databases, combining DDL, DML, DCL, and TCL. It is declarative — specify what you want, the optimizer decides how.

2.2 DDL Statements

CREATE TABLE

CREATE TABLE EMPLOYEE (
    Emp_ID      INT            PRIMARY KEY,
    First_Name  VARCHAR(50)    NOT NULL,
    Last_Name   VARCHAR(50)    NOT NULL,
    Email       VARCHAR(100)   UNIQUE,
    Hire_Date   DATE           DEFAULT CURRENT_DATE,
    Salary      DECIMAL(10,2)  CHECK (Salary > 0),
    Dept_ID     INT,
    FOREIGN KEY (Dept_ID) REFERENCES DEPARTMENT(Dept_ID)

);

2.7 Transaction Basics & ACID Properties

What is a Transaction?

A transaction is a logical unit of work — one or more operations executed as an indivisible whole.

ACID Properties

PropertyMeaningEnforcement
AtomicityAll-or-nothing.Transaction mgr + undo log.
ConsistencyValid state → valid state.Constraint checking at commit.
IsolationConcurrent txns don't interfere.Locks, MVCC.
DurabilityCommitted changes survive crashes.WAL flushed to stable storage.

Transaction States

Active →(success)→ Partially Committed →(flush OK)→ Committed | | (op fails) (flush fails) ↓ ↓ Failed → Aborted (rollback done) → [restart or kill]

SQL Transaction Control

BEGIN TRANSACTION;
-- ... DML operations ...
SAVEPOINT sp1;
-- ... more operations ...
ROLLBACK TO sp1;
COMMIT;

2.10 Concurrency Control

Problems of Concurrent Execution

ProblemDescription
Lost updateTwo txns read same value, both update — one overwrite is lost.
Dirty readRead data from an uncommitted txn that may roll back.
Non-repeatable readReading same row twice gives different values.
Phantom readRe-executing a query finds new rows inserted by another txn.

Isolation Levels

LevelDirty ReadNon-RepeatablePhantomConcurrency
READ UNCOMMITTEDPossiblePossiblePossibleHighest
READ COMMITTEDPreventedPossiblePossibleHigh
REPEATABLE READPreventedPreventedPossibleMedium
SERIALIZABLEPreventedPreventedPreventedLowest

Lock-Based Control & Two-Phase Locking

Shared lock (S): Multiple readers. Exclusive lock (X): Single writer. 2PL: Growing phase (acquire locks) → Shrinking phase (release locks). Guarantees serializability.

Deadlocks

Two txns each wait for a lock held by the other. Detected via wait-for graph (cycle = deadlock). Resolved by aborting one txn (victim).

MVCC (Multi-Version Concurrency Control)

Keeps multiple versions of each row. Readers see the version current at txn start — readers never block writers. Used by PostgreSQL, MySQL InnoDB, Oracle.

Optimistic vs. Pessimistic

ApproachPhilosophyBest for
PessimisticAssume conflicts — lock upfront.Write-heavy, high contention.
OptimisticAssume rare conflicts — check at commit.Read-heavy, low contention.

2.11 Database Recovery Techniques

Write-Ahead Logging (WAL)

Before any change is written to disk, the log record must first be written to stable storage. Log contains: txn ID, old value (UNDO), new value (REDO), COMMIT/ABORT markers.

UNDO and REDO

ActionWhenWhat
UNDOTxn was active at crashRoll back using old values from log.
REDOTxn committed but not flushedRe-apply using new values from log.

Checkpoints

Periodic flush of dirty pages to disk + checkpoint record in log. Limits log scanning during recovery.

2.12 Advanced SQL

Common Table Expressions (CTEs)

WITH DeptStats AS (
    SELECT Dept_ID, AVG(Salary) AS Avg_Sal, COUNT(*) AS Cnt
    FROM EMPLOYEE GROUP BY Dept_ID
)
SELECT D.Dept_Name, DS.Avg_Sal, DS.Cnt
FROM DeptStats DS JOIN DEPARTMENT D ON DS.Dept_ID = D.Dept_ID
WHERE DS.Cnt > 10;

Window Functions

SELECT Emp_ID, First_Name, Dept_ID, Salary,
       RANK() OVER (PARTITION BY Dept_ID ORDER BY Salary DESC) AS Salary_Rank,
       AVG(Salary) OVER (PARTITION BY Dept_ID) AS Dept_Avg
FROM EMPLOYEE;
FunctionDescription
ROW_NUMBER()Sequential number per partition.
RANK()Rank with gaps for ties.
DENSE_RANK()Rank without gaps.
LAG(col, n)Value n rows before current.
LEAD(col, n)Value n rows after current.
NTILE(n)Divide rows into n groups.

CASE Expressions

SELECT Emp_ID, Salary,
    CASE
        WHEN Salary >= 100000 THEN 'Senior'
        WHEN Salary >= 60000  THEN 'Mid-Level'
        ELSE 'Junior'

REVOKE INSERT ON EMPLOYEE FROM user_report;

4.1 Distributed Transactions

Two-Phase Commit (2PC)

Phase 1 — Voting: Coordinator sends PREPARE. Each participant votes YES (writes to durable log) or NO (aborts locally).

Phase 2 — Decision: All YES → GLOBAL COMMIT. Any NO → GLOBAL ABORT.

Blocking problem: If coordinator crashes after Phase 1, participants holding YES votes are stuck — they cannot decide until coordinator recovers.

Three-Phase Commit (3PC)

Adds PreCommit phase between voting and commit. Reduces blocking: participants can determine outcome based on whether they received pre-commit. Trade-off: extra latency, doesn't fully handle network partitions.

4.2 Distributed Query Processing

SQL Query → Parsing → Optimization (Global + Local) → Distributed Execution → Result Assembly

Distributed Join Strategies

StrategyDescriptionWhen to use
Ship-wholeSend entire small table.One table is small.
Semi-joinSend join column values first to filter.Large tables; high selectivity.
Bloom-filter joinSend compact Bloom filter of keys.Very large tables.
Parallel executionIndependent sub-queries simultaneously.Multiple partitions.
Dominant cost factor: Network transfer — moving data between nodes is the most expensive operation.

4.3 The CAP Theorem

Proposed by Eric Brewer (2000), proved by Gilbert & Lynch (2002). In a distributed store, at most two out of three:

PropertyDefinition
Consistency (C)Every read returns the most recent write (linearisability).
Availability (A)Every request gets a non-error response.
Partition Tolerance (P)System works despite network partitions.
Key insight: Partitions are inevitable, so P is not optional. The real choice during a partition: sacrifice C (AP) or A (CP).
ChoiceDuring PartitionExamples
CPError/timeout rather than stale data.HBase, MongoDB, Zookeeper
APBest available (possibly stale) data.Cassandra, DynamoDB, CouchDB
CAOnly without partitions (single node).Traditional single-server RDBMS

Read-your-writesClient always sees its own updates.
Monotonic readsNever see older value after seeing newer.
Monotonic writesWrites by same client applied in order.
SessionRead-your-writes + monotonic reads within a session.

Tunable Consistency (Quorum Formula)

Strong consistency: R + W > N (R = read replicas, W = write replicas, N = total replicas).

4.5 Decision Framework

Is your data safety-critical (money, health, inventory)? YES → Strong consistency (CP / ACID) NO ↓ Can your app tolerate temporary stale reads? YES → Eventual consistency (AP / BASE) NO → Causal or session consistency (middle ground)

4.6 Consensus Protocols — Paxos & Raft

Paxos (Lamport, 1990)

Roles: Proposers, Acceptors, Learners. Two phases: Prepare → Accept. Tolerates < N/2 failures. Notoriously hard to implement.

Raft (Ongaro & Ousterhout, 2014)

Understandable alternative to Paxos. Three sub-problems: Leader election, Log replication, Safety.

Node states: Follower → Candidate (on timeout) → Leader (on majority vote).

Used in: etcd, CockroachDB, TiKV, Consul.

4.7 Distributed Recovery

Each node runs its own WAL-based UNDO/REDO recovery independently. For 2PC coordinator failures:

  • Coordinator reads its log on restart to re-send decision.
  • Participants can ask each other what they voted.
  • Cooperative termination protocol: participants decide without coordinator.

Star Schema

Fact table (centre) contains measures + FKs. Dimension tables (points) describe who/what/when/where. Denormalised dimensions — simple queries, fast joins.

Snowflake Schema

Dimension tables are normalised (e.g. DIM_PRODUCT references DIM_CATEGORY). Saves space; more joins.
