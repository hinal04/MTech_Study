SESSION 1 — Foundations of Structured Data Management

Q1
What are the main problems of using a traditional file system for data management?
▼
  1. Data redundancy — Same data duplicated across multiple files.
  2. Inconsistency — Updating one copy but not others creates conflicting versions.
  3. Difficulty in data access — Each new query may require writing a new program.
  4. Data isolation — Data spread across files in different formats is hard to consolidate.
  5. Integrity problems — No central mechanism to enforce constraints.
  6. Atomicity problems — A crash midway through an update leaves data in a partial state.
  7. Concurrent-access anomalies — Multiple users modifying the same file can corrupt data.
  8. Security issues — File-level permissions are too coarse for field-level access control.
Q2
Define DBMS. What are its key advantages over a file system?
▼

A Database Management System (DBMS) is system software that provides facilities to define, create, maintain, and control access to a database.

AdvantageExplanation
Program–data independenceSchema stored in catalog; storage changes don't require rewriting apps.
Data abstractionUsers work with logical views, not physical details.
Multiple viewsDifferent users see different subsets.
Reduced redundancyCentralised storage + normalisation.
Integrity enforcementConstraints defined centrally, enforced by DBMS.
Concurrency controlMultiple users safely access data simultaneously.
Backup & recoveryRestore to consistent state after failures.
SecurityFine-grained access control (table, column, row level).
Q3
Explain the Three-Schema Architecture. Why is it important?
▼

The ANSI/SPARC Three-Schema Architecture separates a database into three levels:

  1. External Level (User Views) — Individual user perspectives.
  2. Conceptual Level (Logical Schema) — Complete logical structure: entities, relationships, constraints.
  3. Internal Level (Physical Schema) — Physical storage: files, indexes, blocks.

Importance — Data Independence:

  • Logical data independence: Conceptual schema can change without affecting external views.
  • Physical data independence: Internal schema can change without affecting the conceptual schema.

Q7
What are integrity constraints in the relational model?
▼
  1. Entity integrity: No PK attribute can be NULL.
  2. Referential integrity: FK must be NULL or match an existing PK in the referenced relation.
  3. Domain constraints: Every value must belong to its attribute's defined domain.
  4. Key constraints: No two tuples can share the same PK value.

SESSION 2 — SQL Fundamentals and Transaction Concepts

Q13
What is SQL? What makes it different from procedural languages?
▼

SQL (Structured Query Language) is the standard language for relational databases, combining DDL, DML, DCL, and TCL.

Key difference: SQL is declarative — you specify what data you want, not how to get it. The DBMS optimizer chooses the execution plan. Procedural languages require step-by-step instructions.

Q14
Write SQL to create an EMPLOYEE table with appropriate constraints.
▼
CREATE TABLE EMPLOYEE (
    Emp_ID      INT            PRIMARY KEY,
    First_Name  VARCHAR(50)    NOT NULL,
    Last_Name   VARCHAR(50)    NOT NULL,
    Email       VARCHAR(100)   UNIQUE,
    Hire_Date   DATE           DEFAULT CURRENT_DATE,
    Salary      DECIMAL(10,2)  CHECK (Salary > 0),
    Dept_ID     INT,
    FOREIGN KEY (Dept_ID) REFERENCES DEPARTMENT(Dept_ID)
        ON DELETE SET NULL
        ON UPDATE CASCADE
);

Constraints: PRIMARY KEY, NOT NULL, UNIQUE, DEFAULT, CHECK, FOREIGN KEY with referential actions.

Q16
Write SQL queries for five scenarios (filtering, aggregation, subqueries, EXISTS, LEFT JOIN).
▼

a) Employees earning > 70,000:

SELECT * FROM EMPLOYEE WHERE Salary > 70000;

b) Avg salary per dept, > 5 employees, sorted:

SELECT Dept_ID, COUNT(*) AS Emp_Count, AVG(Salary) AS Avg_Salary
FROM EMPLOYEE GROUP BY Dept_ID
HAVING COUNT(*) > 5 ORDER BY Avg_Salary DESC;

c) Above average salary:

SELECT First_Name, Salary FROM EMPLOYEE
WHERE Salary > (SELECT AVG(Salary) FROM EMPLOYEE);

d) Depts with employees (EXISTS):

SELECT D.Dept_Name FROM DEPARTMENT D
WHERE EXISTS (SELECT 1 FROM EMPLOYEE E WHERE E.Dept_ID = D.Dept_ID);

e) All employees with dept names (LEFT JOIN):

SELECT E.First_Name, E.Last_Name, D.Dept_Name
FROM EMPLOYEE E LEFT JOIN DEPARTMENT D ON E.Dept_ID = D.Dept_ID;

▼

A subquery is a SELECT inside another SQL statement.

TypeReturnsExample
ScalarSingle valueWHERE Salary > (SELECT AVG(...))

Q19
Explain the logical order of execution of a SELECT query.
▼
1. FROM       — Identify source tables, perform joins.
2. WHERE      — Filter individual rows.
3. GROUP BY   — Group rows.
4. HAVING     — Filter groups.
5. SELECT     — Choose columns/expressions.
6. ORDER BY   — Sort results.
7. LIMIT      — Restrict row count.

This is why a column alias from SELECT cannot be used in WHERE — WHERE runs before SELECT.

Q20
What is a transaction? Explain the ACID properties in detail.
▼

A transaction is a logical unit of work — one or more operations executed as an indivisible whole.

PropertyMeaningEnforcement
AtomicityAll or nothing.Txn manager + undo log.
ConsistencyValid state → valid state.Constraint checking at commit.
IsolationConcurrent txns don't interfere.Locks, MVCC, timestamps.
DurabilityCommitted = permanent.WAL flushed to stable storage.

Bank transfer example: Debit A and credit B must both succeed (atomicity), total money unchanged (consistency), no one sees partial state (isolation), permanent after commit (durability).

▼
Active → Partially Committed → Committed | | (op fails) (flush fails) ↓ ↓ Failed → Aborted → [restart or kill]
StateDescription

CommittedAll changes permanent.

Q22
What is schema evolution? What challenges does it present?
▼

Modifying a production database schema (adding columns, changing types, adding constraints).

Challenges: Data migration needed, apps may break, views/procedures invalidated, large tables may lock.

Strategies: Expand-and-contract, schema versioning, backward/forward compatibility.

Q23
What is denormalisation? When and why would you use it?
▼

Intentionally reintroducing redundancy to improve read performance.

ScenarioTechniqueTrade-off
Expensive joinsRedundant columns.Faster reads; slower writes; inconsistency.
Repeated aggregationsMaterialised views.Stale data risk.
Read-heavy workloadsDuplicate data per read pattern.Storage + update anomalies.

Rule: Normalise first for correctness, denormalise selectively for measured problems.

Q28
Explain the different distributed database architecture types.
▼
  • Shared-Nothing: Each node has own CPU, memory, disk. Network communication only. Most scalable. (Cassandra, CockroachDB)
  • Shared-Disk: All nodes access common storage (SAN). Easier sharing; storage bottleneck. (Oracle RAC)
  • Shared-Memory: All processors share memory & disk. Limited scalability. (SMP machines)
Q29
What is data fragmentation? Explain horizontal and vertical fragmentation.
▼

Horizontal: Split by rows (selection condition). Reconstruction = UNION.

Vertical: Split by columns (PK always included). Reconstruction = Natural JOIN on PK.

Hybrid: Both horizontal and vertical applied.

Correctness: Completeness (every tuple in ≥1 fragment), Reconstruction (original can be rebuilt), Disjointness (no overlap preferred).

SESSION 4 — Distributed Transactions and Consistency Models

Q34
Explain the Two-Phase Commit (2PC) protocol in detail.
▼

Phase 1 — Voting: Coordinator sends PREPARE. Participants vote YES (log changes, prepare) or NO (abort locally).

Phase 2 — Decision: All YES → GLOBAL COMMIT. Any NO → GLOBAL ABORT. Participants ACK.

Blocking problem: If coordinator crashes after Phase 1, participants holding YES votes are stuck — cannot commit or abort until coordinator recovers. They hold locks and wait.

Q35
How does Three-Phase Commit (3PC) improve on 2PC?
▼

3PC adds PreCommit between voting and commit:

  1. CanCommit? — Ask participants.
  2. PreCommit — All agree → send pre-commit (prepare, don't commit).
  3. DoCommit — Final commit.

Improvement: Participants can determine outcome based on whether they received pre-commit.

Limitation: Extra latency; doesn't fully handle network partitions. Modern systems use Paxos/Raft instead.

Q36
Describe the key steps and cost factors in distributed query processing.
▼

Steps: Parsing → Optimisation (global + local) → Distributed Execution → Result Assembly.

Cost factors: Network transfer (dominant) > Local I/O > Local CPU.

Join strategies: Ship-whole (small table), Semi-join (send join keys first), Bloom-filter join, Parallel execution.

Q37
State and explain the CAP theorem.
▼

CAP (Brewer 2000, proved Gilbert & Lynch 2002): at most 2 of 3:

PropertyDefinition
ConsistencyEvery read returns the most recent write (linearisability).
AvailabilityEvery request gets a non-error response.
Partition ToleranceSystem works despite network partitions.

Key insight: P is not optional. Real choice: CP (errors over stale data — HBase, Zookeeper) or AP (serve stale data — Cassandra, DynamoDB).

Most real systems offer tunable consistency.

Q40
Explain eventual consistency and its variants.
▼

If no new updates, all replicas eventually converge. No guarantee about when.

VariantGuarantee
CausalIf A causes B, everyone sees A before B.
Read-your-writesClient always sees its own updates.
Monotonic readsNever see older value after seeing newer.
Monotonic writesSame client's writes applied in order.
SessionRead-your-writes + monotonic reads within session.
Q41
What is tunable consistency? Give an example with Cassandra.
▼

Choose consistency level per-query, trading latency vs. freshness.

LevelMeaning
ONE1 replica ACK (fastest, weakest).
QUORUMMajority ACK (balanced).
ALLAll replicas ACK (strongest, slowest).
LOCAL_QUORUMQuorum in local DC only.

Strong consistency formula: R + W > N. Example: N=3, W=2, R=2 → 4>3 ✓

Q42
How do you choose between strong and eventual consistency?
▼
  1. Safety-critical data? (money, health) → Strong (ACID/CP).
  2. Tolerate stale reads? → Eventual (BASE/AP) for scale + low latency.
  3. Middle ground? → Causal or session consistency.

Best practice: Mix models — ACID for payments, eventual for recommendations, session for profiles.

Q44
Quorum calculation: N=5, W=3, R=3 vs R=2. Is strong consistency guaranteed?
▼

Case 1: W=3, R=3: R+W = 6 > 5 → Yes, guaranteed.

Case 2: W=3, R=2: R+W = 5 = 5 → No, NOT guaranteed. Must be strictly greater. Fix: increase R to 3 or W to 4.

Q46

▼

Q47
Billions of order rows — how would you evolve the architecture?
▼
  1. Optimise RDBMS: Indexes, materialised views, archive cold data.
  2. Vertical scaling: Bigger server (RAM, SSDs).
  3. Read replicas: Primary for writes, replicas for reads.
  4. Horizontal partitioning (sharding): Hash by customer_id or range by date.
  5. Distributed SQL: CockroachDB, YugabyteDB — transparent sharding + ACID.
  6. Polyglot persistence: RDBMS for txns, data warehouse for analytics, Redis for caching.
Q48
Design an ER diagram for a university database, then map to relational tables.
▼

Entities: STUDENT, COURSE, INSTRUCTOR, DEPARTMENT.

Relationships: enrols (M:N), teaches (1:N), offers (1:N), belongs_to (N:1).

CREATE TABLE DEPARTMENT (Dept_ID INT PRIMARY KEY, Dept_Name VARCHAR(100));
CREATE TABLE INSTRUCTOR (Instructor_ID INT PRIMARY KEY, Name VARCHAR(100),
    Dept_ID INT REFERENCES DEPARTMENT(Dept_ID));
CREATE TABLE COURSE (Course_ID INT PRIMARY KEY, Course_Name VARCHAR(100),
    Credits INT CHECK(Credits>0), Dept_ID INT REFERENCES DEPARTMENT(Dept_ID),
    Instructor_ID INT REFERENCES INSTRUCTOR(Instructor_ID));
CREATE TABLE STUDENT (Student_ID INT PRIMARY KEY, Name VARCHAR(100),
    Email VARCHAR(100) UNIQUE, DOB DATE);
CREATE TABLE ENROLMENT (Student_ID INT, Course_ID INT, Grade CHAR(2),
    Semester VARCHAR(20),
    PRIMARY KEY(Student_ID, Course_ID, Semester),
    FOREIGN KEY(Student_ID) REFERENCES STUDENT(Student_ID),
    FOREIGN KEY(Course_ID) REFERENCES COURSE(Course_ID));

Rules: Strong entities → tables. 1:N → FK on "N" side. M:N → junction table.

Q50
Short-answer rapid-fire (10 questions).
▼
  1. Three levels of ANSI/SPARC? External, Conceptual, Internal.
  2. 1NF requires? Atomic values — no multi-valued or composite in a cell.
  3. Candidate key vs Primary key? Candidate = any minimal superkey. Primary = the one chosen.
  4. Referential integrity? FK must be NULL or match an existing PK.
  5. SQL clause that filters groups? HAVING.
  6. DELETE vs DROP? DELETE removes rows (structure stays). DROP removes entire table.
  7. MVCC stands for? Multi-Version Concurrency Control.
  8. CAP: which property is always required? Partition Tolerance (P).
  9. Strong consistency formula? R + W > N.
  10. Three NoSQL categories? Key-Value, Document, Column-Family (or Graph).
